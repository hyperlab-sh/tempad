# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- `tempad agent spawned --parent <lead session id> [--child <child session id>] --role developer|senior-dev|reviewer|mechanic|researcher|squad-leader --harness claude|pi [--model <name>] [--effort <level>] [--ref <bead id>] [--quest <quest id>] [--title "<text>"]` records one `agent.spawned` fact event (a fresh ULID subject; payload `parent_session_id`, `child_session_id`, `role`, `harness`, `model`, `effort`, `ref`, `quest_id`, `title`, `at`; omitted flags absent, never null) so a lead can mark a spawn the moment it happens. With `--child` and a resolved quest (`--quest`, or the parent's single active declared quest when `--quest` is omitted) it also declares that quest for the child in subagent scope through the same `declareQuest` as `tempad quest declare --parent`, `declaredBy: "agent"`, plan `[title]` — one command at launch time covers both events. Several active parent quests and no `--quest` records the spawn only and prints the candidates; no `--child` records the spawn only. The `w5 context` line resolves a session exactly like `buildWindow` does — the latest declaration decides the shape (a parent id means subagent: own quest first, else the parent's active quests; no parent means the session-scope fold), so a spawned agent's hook context shows the quest it was spawned under instead of `none`, and a child reassigned later shows the new assignment. Quest resolution no longer depends on `--child` (a pi fact with no child id still carries `quest_id` when the parent has one active quest). The launchers (`bin/tl-launch.sh`, `bin/tl-launch-pi.sh`) create the spawn log directory when missing and fall back to stderr when it is unwritable, so a missing `logs/` never silently skips the recording.

### Fixed

- A declared window's later segments no longer open duplicate stints for one outcome. The declared `segment.stint` selector accepts `"segment:<n>"` (the stint an earlier segment of the same response opened, 1-based, renumbered by `validateResult` after overlap drops exactly as the inference selectors), and a segment that named no stint at all, or an explicit `new:` that names the previous stint's own quest, continues the previous segment's stint only when **both** gates hold: `isSwitch` is false and the resolved quest is unchanged — a same-quest segment marked as a switch still opens its own stint, because `isSwitch` is an outcome boundary even within one quest. The model had no way to name a stint the window itself opened. Each such landing counts `sameWindowReuse` and logs `w5 stint resolved within window:`. A reference that names nothing (out of range, or built by hand) opens a new stint and counts `unknownStintId`, like an unknown alias. `new:` outcome matching for reuse now folds at most one lone sentence-ending mark (a trailing `.`, `!` or `?` and whitespace) on both sides, so a rephrased outcome joins its stint instead of splitting it — but a run of marks (`..`, `done!!`) or a path-like tail (`v1.2.`, `src/w5/apply.ts.`) is a meaningful technical token and never folds. The mark folds only when a plain alphanumeric word precedes it — a standalone dot (`Resolve path .`), a backslash path tail (`C:\build.`) and version-like tokens stay untouched. `new:` reuse is keyed on `(quest, normalized outcome)`: a stint whose quest differs from the segment's is never reused, whatever the outcome text, so an identical `new:` on another quest opens that quest's own stint instead of putting the trace under the previous quest.

- A doubt (`belongs: false`) no longer strips the quest from the work it flags. The stint stays on the quest the segment was judged against (the one the model named, else the session's current one, a subagent's own before its parent's), the trace is marked doubted (`traces.doubt`), and a `belongs` question is still asked when the segment carries a quoted `trigger`. Before, the stint was opened with no quest and stayed that way when the question expired. `tempad answer --belongs` and `--quest` clear the doubt on the trace (`--quest` also moves the stint, as before), an expiry leaves both the quest and the doubt, and `tempad rebuild` reproduces the flag from events (no migration). A doubt the model gave no quoted `trigger` for, or one the validator made up from an unrecognized quest alias, is recorded and counted in `doubts` but no longer asks a question; the `w5 doubt:` line says why (`no question: no trigger` or `no question: unrecognized alias`) and `doubts_silent=` in `w5 eval` counts them. A missing quest alias with several quests active still asks when there is a trigger. `tempad review` lists doubted stints in their own section with the quest title, guess and trigger when there is one; a `belongs: false` segment that names an active quest alias now keeps it through validation instead of having it nulled.

### Changed

- A quest declaration now covers its session from the session's start, not from the moment it was declared: the first declaration of a session is active from `claude_sessions.started_at`, a later one starts at its own event unless every earlier quest was already `--done` (then it starts at the last `--done`, with no gap), and `tempad quest declare --since <iso>` overrides the start (never after the declaration, not valid with `--done`). Models declare late, often at session end, and on the real database 511 of 598 quest-less stints in declaring sessions had opened before the first declaration; every window of such a session now runs in declared mode with the quest offered, the plan items and the alias. Subagent declarations follow the same rule within their own session. `tempad w5 backfill` re-classifies the windows a covering declaration reaches that were classified before it was recorded, replacing what the earlier pass recorded for just those windows (traces, and the stints and unconfirmed quests only they held, retracted as events; stints on a declared or confirmed quest are kept) and logging one line per replaced window; `tempad scry` counts them in its backfill recommendation (inferred-mode sessions in neither). A session's stale windows are replaced together or not at all: if any live trace overlapping them is not wholly inside them (a live-runner trace spanning chunks, or one running past a chunk's messages) or sits on a quest that was declared, confirmed or named by a declaration, the whole group is declined, with nothing retracted, nothing rerun and one log line naming the session, window range and reason; `tempad scry` does not count declined windows as pending. Existing databases get the stale windows derived from their declarations by migration 0026, no rebuild needed. A quest ended with `--done` (or in a stretch `--since` left uncovered) is no longer returned as the current quest by `currentDeclaredQuest*`, so evidence after the `--done` is unattributed in reports.

## [0.3.1] - 2026-10-18

### Removed

- `tempad w5 backfill --reclassify` (with `--to`, `--backup` and `--dry-run`, which existed only for it) is gone: retracting a whole time range is not a product feature, it was written to repair one classifier incident, and a mistake is corrected per item instead (`tempad quest retract`, or `tempad quest reword` for a title). `w5 backfill [--days <n> | --from <iso>] [--model <name>] [--force]`, `w5 eval` and `w5 dedupe` are unchanged, and the `retracted`, `question.answered` and `stint.continuation_cleared` events a run already wrote still replay.

### Fixed

- An inference window that the classifier splits into several segments no longer turns into one stint per segment, all but the first with no quest. The prompt lists only stints and quests that existed before the window, so a later segment had no way to name the stint or quest an earlier segment had just opened: four review rounds of one brief came back as four stints, and `tempad w5 backfill --reclassify` of Oct 2-5 raised the quest-less stints of those sessions from 68 to 82. A segment can now name an earlier one as `"segment:<n>"` in `matchedStint`, `continuesStint` or `matchedQuest` (renumbered when a segment in the context-only tail is dropped; a reference to itself, a later or a dropped segment is ignored). A quest id in `matchedStint` or `continuesStint` (the commonest selector mix-up) lands on the stint an earlier segment of the window opened for that quest, rather than opening a second one or continuing an older stint of another session. A segment that says it did not switch (`isSwitch: false`) and names no stint stays on the previous segment's stint when their quests agree; a reason the model gave for a new stint is overridden only when it also names the previous stint's own quest, and the discarded reason is logged. A quest proposed again in one window with the same title and outcome is reused rather than created twice (the same title for another outcome is a quest of its own), and a quest-less stint the window opened can be given a quest the window offered or created. `tempad w5 eval` prints how often this happened as `same_window_reuse=`. Ids from before the window are still checked against what the window offered; declared mode is unchanged.

## [0.3.0] - 2026-10-18

### Added

- `tempad schedule install | remove | status [--json]` runs `tempad sync` every hour for you. macOS gets a LaunchAgent (`sh.hyperlab.tempad.sync`, `StartInterval` 3600 and `RunAtLoad`, loaded with `launchctl bootstrap gui/<uid>`, unloaded with `bootout`), Linux a systemd user service and timer (`OnCalendar=hourly` with `Persistent=true`, so a missed hour runs when the machine is back; enabled with `systemctl --user enable --now`, and `install` starts the first run right away, as `RunAtLoad` does on macOS); other platforms get an error. The job runs the same tempad you invoked (the symlink-resolved entry script, so a linked checkout works, run by the `bun` your `PATH` finds when it lives in a stable place such as `~/.proto/shims` or `~/.bun/bin` (under proto the shim's versioned directory on `PATH` is skipped and `$PROTO_HOME/shims/bun` is used, and the checkout's `.prototools` pin is carried into the job as `PROTO_BUN_VERSION` so it runs the pinned Bun, not proto's global default; `status` prints the Bun version the job will use and reports a checkout pin that moved since install; the held `sync.lock` is touched every 5 minutes so a sync past the 6 hour ceiling is not taken over), otherwise the Bun binary in use with a warning when its path carries a version that an upgrade removes), with an absolute `PATH`, `TEMPAD_HOME` when set, and stdout/stderr appended to `TEMPAD_HOME/logs/sync.log`. `install` twice rewrites and reloads, `remove` when nothing is installed exits 0, and `status` reports installed, loaded, the last run and its exit code (`--json` for scripts; exit 0 only when everything is fine). `install` refuses a disposable `bunx`/temp copy and an unconfigured home, makes a relative `TEMPAD_HOME` absolute, and warns when a variable the sync needs is set in your shell but missing from `TEMPAD_HOME/.env` (the job does not see shell exports). `tempad scry` now warns, and recommends `tempad schedule install`, when a collector is stale and no schedule is installed; with fresh collectors it says nothing.
- `tempad w5 backfill --reclassify --from <iso> [--to <iso>] (--dry-run | --backup <path>)` redoes a range on the real database: it retracts (as events, nothing is deleted) what w5 inferred for the sessions in range and classifies them again, so stints fragmented by the id mix-up can be repaired. It also closes the open questions of the retracted traces (they are no longer listed by `tempad review`, asked by the hook or answerable with `tempad answer`) and clears the `continues` link of a surviving stint whose origin it retracted. Sessions are left alone and listed, with the reason, when they are still active (ended within `stint_idle_minutes`), have a declared quest, have a stint on a confirmed quest or on one a person changed (so a quest you confirmed never loses its stints to a re-run), have a trace w5 did not write, or have an answer or manual quest assignment by a person; `--dry-run` shows the count per reason. It holds the w5 runner lock for the whole run and exits 1 if another run holds it, refuses to run without `--backup <path>` (exit 2; a checked `VACUUM INTO` copy taken first), and `--dry-run` shows the counts without writing, without an API key and without the lock; `--dry-run` with `--backup` is a usage error. The lock is refreshed before every window, so a long run keeps it; while it runs, live sessions are not classified (their jobs stay queued and run afterwards), and the command says so. The questions it closes count as `resolved_by_context` in `tempad scry`'s question breakdown, like the ones context resolved.
- `tempad help <command> [<subcommand> ...]` and `tempad <command> [<subcommand> ...] --help` print the usage of that command or subcommand only (all `tempad quest ...` lines for `quest`, one line for `w5 backfill`) instead of the full list. `tempad help`/`--help` still print every command and now end with `Run tempad help <command> for one command.`. An unknown command or subcommand exits 2 with the unknown part named and the nearest usage on stderr. The usage texts live once in `src/usage.ts`.
- `tempad scry [--json] [--days <n>] [--fast]` is a read-only health check of the data. It reports Health (config, schema version, `PRAGMA quick_check`, whether every projection matches a replay of the event log, collector freshness, failed or stuck w5 jobs, windows no classification covers, expired questions and unconfirmed quests waiting for you, and unpushed or pending sync state), Stats, and Recommendations, each a command to paste plus one line on why (`tempad sync claude`, `tempad w5 backfill --from <time>`, `tempad rebuild`, `tempad sync --push`, `tempad review`, ...). Exit 0 when nothing failed, 1 when a check failed, 2 on a usage error (`--days` takes 1 to 3650). The projection check also fails when a projection table or column is missing, not only when rows differ. The backfill it recommends is the same plan `tempad w5 backfill` runs. It opens `tempad.db` read-only, so it applies no migration, repairs no trigger, writes no host slug and never touches the network or loads `@libsql/client`. `tempad w5 eval` is only listed as conditional (after changing `[w5]` settings, the prompts or the tempad version): the database does not record what produced a classification, so the data cannot say an eval is due. `--fast` skips `quick_check` and the replay. On a 274 MB database with 64,000 events it takes about 1 s (about 0.2 s with `--fast`).
- `tempad w5 backfill --from <iso>` classifies sessions that ended at or after an absolute time, as an alternative to `--days <n>` (which counts back from the moment you run it). The two cannot be combined and anything but ISO 8601 (`2026-10-01` or `2026-10-01T10:00:00Z`, with `Z` or a `+-HH:MM` offset) is a usage error (exit 2). `tempad scry` recommends this form, so its command covers the oldest unclassified session however long you wait before pasting it.
- `tempad sync --forget` is the off switch for a host that leaves sync for good. After you remove `[sync]` from `tempad.toml`, it drops the 18 sync triggers, every tombstone, the pull cursors and the server identity in one transaction, and the database stops tracking changes for a server you no longer use. It refuses with exit 1 while `[sync]` is still enabled, and while deletes or changes have not reached the server (`N deletes / M changes never reached the server`) unless you pass `--force`. It prints `sync: forgot triggers=<n> tombstones=<n> cursors=<n> meta=<n>` (or `sync: nothing to forget`), needs no token, never touches the network, and leaves your data and the `sync_*` columns alone. The database remembers the id of every server it left (a growing set) and refuses to sync with any of them again (`ForgottenServerError`): rejoining would restamp every row as new and overwrite edits other hosts made since, and bring back rows they deleted. Point `[sync]` at a fresh server instead, start from an empty `tempad.db` and pull, or run `tempad sync --rejoin <server-id>` to accept the overwrites for one server. A second `--forget` is not blocked by rows written after the first.
- `tempad quest retract <id> --reason "..." [--force]` (alias `quest delete`) undoes a quest created by mistake. `abandon` is for work that was dropped and keeps the quest in reports; retract appends a `retracted` event so the quest disappears everywhere. The reason is required. It refuses (exit 1) when the quest has live stints or traces, child quests (serving, advancing, deviating from or merged into it) or was itself merged into another, unless `--force`, which retracts those dependents too (traces, stints, child quests); the quest it was merged into is untouched. Retracting an already retracted quest prints a message and exits 0. The quest skill now says to retract a mistaken quest instead of abandoning it.

### Changed

- `tempad w5 eval`'s reset on its throwaway copy now also closes the open questions of the traces it retracts and clears the `continues` link of a kept stint whose origin it retracted (the cascade is shared with `--reclassify`), so `continues_links=` can be lower than before when a kept stint continued a retracted old-cohort one; the other metrics are unchanged.
- Inference-mode windows offer at most `[w5].memory_quests` open quests (default 20), ranked this session's, then the project's, then the rest, each newest first, instead of all of them (~475 quests, 66 KB of prompt on real data). The quest of every stint the window offers is always listed, past the cap if need be. Set it higher to restore the old behaviour; `0` offers only those.
- tempad now needs **Bun 1.4.2 or newer** (`engines.bun` was `>=1.3.14`). CI, `.prototools`, `.moon/toolchain.yml` and `packageManager` pin 1.4.2, the newest 1.4 patch older than two weeks, so local runs (which already got 1.4.x through the proto shim) and CI use one TOML parser. 1.3.14 accepted malformed `tempad.toml` that 1.4 rejects (`[w5` at end of file, `[sync]]`, a duplicate `[a]` table). If you are on 1.3.x, run `bun upgrade`.

### Fixed

- `buildWindow` is about 20 times faster on a database with thousands of stints that never closed (1.7 s to under 0.1 s per window on real data): the latest trace of every stint comes from one ranked pass over `traces` instead of a correlated scan per stint. A tie on `ended_at` is now broken explicitly (latest start, then highest id) instead of by whatever the sorter returned.
- `tempad w5 backfill` (inference fallback) no longer fragments one stretch of work into a stint per window when the classifier mixes up the ids it is offered. A quest id named as the stint (or a stint id as the quest) now resolves to the session's stint of that quest, and a closed stint named as `matchedStint` becomes a `continues` link instead of an unlinked new stint. A genuinely unknown id still opens a new stint and counts in `unknown_activity_ids`.
- A stint that a later window already closed, named in `matchedStint` or `continuesStint` by a segment that ended before it closed, is reused instead of opening an overlapping `continues` stint (matters when a range is classified again). A segment that ran past the close continues it with a `continues` link, so no trace lands after its stint's `closed_at`.
- A matched stint that has no quest now takes the open quest the classifier names for it (`quest_attached_on_matched=` in `w5 eval`), instead of staying unattributed and counting a doubt in every window.
- `[w5]` counts (`memory_quests`, `memory_stints`, `overlap_messages`, ...) reject values such as `1e20`, which SQLite refuses as a `LIMIT` and which failed every window.
- A `tempad schedule` job installed on the proto shim before the Bun pin was carried into the job makes `tempad schedule status` exit 1 with `... carries no pin; run \`tempad schedule install\``, once the checkout has a `.prototools` pin. That is the intended prompt to reinstall so the job runs the pinned Bun.
- `tempad w5 backfill --help` crashed with a stack trace (`ERR_PARSE_ARGS_UNKNOWN_OPTION`), as did `--help` on any nested subcommand: only the first argument was checked. `--help`/`-h` now works at any depth (`w5 hook install -h`, `quest declare --help`) and never runs the command.
- Two `tempad sync` runs at once (a scheduled one overlapping a manual one) no longer run the same collectors side by side. Collecting syncs now take `TEMPAD_HOME/sync.lock` (the `w5.lock` mechanism) and the second one prints `sync: another sync is already running; skipping` and exits 0 (75 for `sync --push`/`--pull`, which asked for exactly that and got nothing). A lock left by a killed sync (Ctrl-C, SIGTERM) is cleared by the next sync at once, because its process is gone (clearing is itself serialized by `sync.lock.clearing`, so two runs cannot remove each other's fresh lock, and the same handoff now serializes the age-based clear of `sync.lock` and `w5.lock`, so two runs that both judge a lock stale can no longer both take it); a lock with no readable pid, or one past 6 hours, falls back to the 30 minute and 6 hour rules. `--forget` and `--rejoin` are unaffected.
- A `tempad.toml` value of the wrong type no longer falls back to its default without a word. `stint_idle_minutes = "abc"` still keeps the default so tempad keeps working, but now prints `<path to tempad.toml>: [w5].stint_idle_minutes must be a number, 0 or more, got "abc" (a string); using the default 45. Fix the value.` once on stderr, in the style of the renamed-key warning, and `tempad scry` reports it as a `warn` on its Config check with the same line (`N setting(s) of the wrong type (default used) in tempad.toml`). It covers every `[w5]` key (a `backend`/`mode` that is not one of its values, `[w5]` itself not being a table), a `joined`/`description` on a `[[parties]]` entry that is not a string, and `[[projects]]`: a `name` that is not a string (it used to be stored as written) or an `org`/`project` of a pattern rule is ignored with a warning, while a non-string `path`, `pattern` or path-rule `org`/`project`, an empty `path`/`pattern`, and `projects`/`repositories`/`boards` that are not arrays of tables are now an error instead of a stored number or a `TypeError`. Numbers must be finite (`nan` and `inf` are TOML numbers): counts (`watch_turns`, `ask_expire_turns`, `overlap_messages`, `memory_stints`) whole numbers of 0 or more, minutes and hours 0 or more, `timeout_seconds` above 0, `backfill_days` a whole number from 1 to 3650. `tempad scry` now also reads the `[[projects]]` rules for its Config check, so a rule the collectors would reject fails it. `[sync]` and `--declare` files already rejected wrong types with an error and are unchanged.
- A finished w5 job now records when it actually finished. `w5_jobs.finished_at` of a job that completed (or failed while running) was the moment the run started, the same as `claimed_at`, so every done job showed a duration of zero. Jobs written before this fix keep that value. `w5_runs.last_run_at`, which the throttle measures from, is unchanged.
- A w5 job no longer fails permanently with `classifier result invalid: segments[0].quest: expected an active quest alias when belongs is true`. It happened on a window of a session with no active quest (nothing declared yet, a quest declared only after the window, or every declared quest ended with `--done` or retracted) when the model still answered `belongs: true`, and the retry got the same answer. The segment's `quest` is now dropped, the window's work is recorded with no quest, and the session is asked once to declare one (once the window's work reaches the minimum stint length), as already happens when the model answers `belongs: false` there. It counts in `selector_defaulted`. A model that names a quest the window never offered in such a window no longer raises a `belongs` doubt per segment either.
- A w5 job no longer fails permanently for three more reasons the classifier's answer could be rejected for. A segment whose timestamps stray outside the window (the model reached into the context-only tail before it or past the last message) is now clamped to the window, or dropped when it lies wholly in the tail or when clamping leaves it no time (timestamps are compared as instants and a kept pair is stored as canonical UTC, so an offset like `12:05-03:00` is read as 15:05Z and `15:30:00Z` matches a message at `15:30:00.000Z`); a start after the last message, a start after the end and a timestamp that does not parse are still errors, reported with a retry hint. A `sessionNote` over 300 characters is cut to 300 with an ellipsis (never in the middle of an emoji). `belongs: false` with an empty `guess` gets the placeholder `something else`, so the doubt still reaches `tempad review`. Each repair is counted (`tempad w5 eval` prints `overlap_dropped=`, `bounds_clamped=`, `session_note_truncated=`, `guess_defaulted=`). `apply.ts` no longer has a second overlap check of its own. On the 316 jobs that failed with the missing-alias message on one real database, the error messages show every one of them is now repaired (an estimate: the raw responses were never stored).
- A failed w5 job now keeps the first 500 characters (never splitting an emoji) of the response that failed it, after the error message in `w5_jobs.error`, so the next failure of this kind can be diagnosed from the database. `tempad scry` still groups failures by their message alone.
- A w5 job no longer fails with `unknown claude session: <id>` when the hook fires before `tempad sync claude` has stored the session. The detached `w5 run` now looks for the session's transcript itself (`<claude dir>/projects/<project>/<id>.jsonl` under `CLAUDE_DIRS`), collects that one file, then classifies; the hook stays as fast as before, since the lookup runs in the background process. A session with no transcript on disk still fails the job, now as `unknown claude session: <id> (no transcript found under CLAUDE_DIRS, or it holds no messages)`. On a copy of a live database, 1,338 of the 1,369 `unknown claude session` failures of the last 7 days (14,000 of 14,338 all time) were for sessions whose transcript is on disk and would have run. Existing failed rows are left as they are: they hold no work, and `tempad w5 backfill` classifies the windows they never covered (`tempad scry` counts them under classification coverage).
- A w5 job left `running` by a runner that crashed is no longer stuck for good. Each run of `w5 run` first reaps jobs claimed more than 30 minutes ago (the classifier gives up after 3 minutes, so a live job never gets near it): the job goes back to the queue for another attempt, and fails with `lease expired: ...` after 3 attempts, or at once when it was requested over 24 hours ago, because classifying a day-old window as if it were live would ask questions in a long-dead session (`tempad w5 backfill` covers its session). A session never holds two queued jobs after a reap (a stale job whose session was enqueued again is failed as superseded and its `session_end`/`forced` carried over), and a reaped job's `finished_at` is its claim time, so reaping does not count old failures as recent. Migration 0025 adds `w5_jobs.attempts`. `tempad scry` recommends `tempad w5 run` when a job is stuck, and no longer tells you to `sync claude` for a session the runner already searched for.
- A w5 job can no longer run twice. A runner that slept through its lease (a laptop closed mid-classification) could finish after another runner reaped and re-claimed its job, and both appended the same traces, stints and questions, which cannot be removed. A result is now applied only in the transaction that first checks the runner still holds the job's claim (claim time and attempt number), together with marking the job done; a runner that lost it discards its result, and a late failure no longer overwrites the job's new state. A failure while applying also rolls back every event that job wrote. `w5.lock` is no longer judged by file age alone: it is stale only when it is over 30 minutes untouched and the pid inside is not running (or over 6 hours old whatever the pid), and the runner touches it before each job.
- Two `w5 run` processes can no longer both claim one job or both take `w5.lock`. Claiming a job is one `UPDATE ... RETURNING` statement (it was a select, an update and a read-back, so two runners could both read back the later claim and both pass the claim check), settling a job is one guarded `UPDATE` rather than a check followed by a write, and the lock is created with `O_EXCL`. A finishing runner removes `w5.lock` only if it still holds its own pid, the idle-stint close that runs before classification now checks the claim too, and the log says when a runner lost its claim or why a lock was judged stale (dead runner or the 6 hour ceiling) instead of reporting a failed run or a dead runner.
- A side quest declared with `tempad quest declare --new <title> --deviates-from <quest>` is now recorded on the new quest, naming the quest it left. It used to be stored the other way round, on the quest being left, with the new quest's id in its stint column, so `quest list --side`, the classifier's recent side quests and the daily report's "Side quests" section showed the wrong quest (and overwrote that quest's own side-quest relation, if it had one). Old events are not rewritten: the projection recognizes the old shape and reads it the right way round, and migration 0024 adds the `quests.deviates_from_quest_id` column and re-projects the `quests` table from the event log while it migrates, so existing rows are repaired on the first run of the new version with nothing to do by hand. A host still on an older version keeps writing the old shape until it upgrades; the result is the same once it does. `tempad quest branch <side> --deviates-from` now takes a quest id as well as a stint id, and `--at <iso>` to place the branch in the past, so a quest can be made a side quest of another after the fact. `quest list` marks each side quest with `side quest of <parent>`, and `tempad answer --origin current` records the quest being left instead of a `null` stint when the session has no earlier stint of it. `quest retract` no longer needs its workaround for the inverted shape.
- `openDatabase` no longer leaks the SQLite handle when a migration throws: it closes the connection and rethrows, as it already did for a failing trigger check or host-slug write.
- `tempad sync --rejoin ''` and `--rejoin <unknown id>` now exit 1 with a message on stderr instead of exiting 0 as if something had happened. `tempad sync --rejoin` with no value and any unknown sync flag (`--bogus`) now print one `sync: <reason>` line plus the usage and exit 2, instead of a raw `parseArgs` stack trace.
- The prompt hook no longer tells a session that has declared a quest that it has none. A `declare` question queued before the declaration was still asked afterwards and printed `w5 has no declared quest for this session` right under `active quests: <title> [Q1]`. The w5 run now resolves such a question once the session has an active quest (a quest ended with `--done` or retracted does not count, so the question stands then), and `w5 context` and `tempad review` skip it on the same rule.
- Commit dates with a UTC offset of +-15:00 or more (never emitted by git, only by imported history) were left in offset form by migration 0021, because SQLite's `strftime` returns NULL for them, while a host that pulled the same row stored UTC. Migration 0023 now rewrites them to the same UTC text, once, atomically with the version bump, without restamping or re-dirtying the row, so every host holds one text per instant and later opens pay nothing.
- `tempad sync` reports a failed push or pull the same way every time: the exit code is 1 and stderr gets one `sync: push failed: <reason>` line (`sync: pull failed: <reason>` for `--pull` alone). It covers a missing `@libsql/client` package, an unreachable server, a rejected token and any server error. The collectors' results are kept, and the token is scrubbed from the reason.
- Retracted quests no longer show up. `quest list` hides them (`--all` shows them marked `(retracted)`, and `--side`/`--unconfirmed` hide them), the classifier is no longer offered them in inferred mode, reports no longer name a retracted quest on a stint, and `confirm`, `merge`, `branch`, `return`, `pause`/`resume`/`done`/`abandon`, `reword`/`replace`/`edit`/`end`, `declare --done` and `answer --quest` refuse one. A retracted quest or stint no longer counts as an attachment for the edit-intent guard.
- `tempad <command> extra` no longer runs a command that takes no positionals with the stray word, throws a stack trace or prints every command's usage. A path that takes fewer positionals than given (`sync --full bogus`, `rebuild bogus`, `schedule status bogus`, `w5 dedupe bogus`, `report daily bogus`, ...) now exits 2 with that command's own usage on stderr. Usage errors of `sync`, `report`, `skill` and `project` print their own command's usage instead of the whole list.
- The forms `tempad answer` and the hand-backs tell a session to run are now runnable exactly as printed. `--origin current --trigger ... --kind ...` is valid only with a new quest (`--quest new:"<title>"`), so the answer usage and the hook, `tempad review` and classifier-question hand-backs print the existing-quest and new-quest forms as separate lines under `Reply with one of:`, and the declare hand-back lists `--quest <quest-id>` and `--new` on separate lines instead of `<id>|--new`, whose bare `|` a shell reads as a pipe. `--kind <waiting|blocker|curiosity|unknown>` no longer carries a pipe inside optional brackets. The `tempad answer` usage error prints `usage:` on its own line with every form indented alike.
- A multi-step upgrade of a sync-enabled database can no longer leave a window with no mirror triggers. Migration 0022 drops the 18 sync triggers, and each migration used to commit on its own, so a process holding the database open (a w5 hook, a collector) could write mirror rows between 0022 and a later migration that nothing stamped, tombstoned or pushed. Every pending migration from 22 on now applies in one transaction that reinstalls the triggers once, at its end; a failure from 22 on rolls back to the version below with its triggers. Latent in 0.2.0, where 22 was the newest.
- The Claude collector and `tempad project register|reresolve` normalize each session path once instead of twice (an `existsSync` plus a `realpathSync` per ancestor, per session).

### Migration

- `0023_normalize_wide_offset_commit_dates.sql` has no SQL: its work is a TypeScript step that runs in the same transaction as the version bump. It rewrites `gh_commits.authored_at` and `committed_at` that 0021 left in offset form because SQLite's `strftime` returns NULL for an offset of +-15:00 or more, to the UTC text JavaScript writes. It runs once per database, restamps and dirties nothing, and rolls back with the version if it fails.
- `0024_side_quest_parent.sql` adds `quests.deviates_from_quest_id`, the quest a side quest left, next to `deviates_from_stint_id` (which keeps naming a stint only). A TypeScript step replays the `quests` table from the event log in the same transaction, so existing rows, including side quests `quest declare` stored inverted before this change, are repaired with no `tempad rebuild`.
- `0025_job_attempts.sql` adds `w5_jobs.attempts INTEGER NOT NULL DEFAULT 0`, counted on every claim, so a job whose runner died is requeued a bounded number of times (3) before it fails. A job claimed before the migration counts 0 and gets one attempt more, which is harmless.
- Comment-only edits to `0016_impacts_session.sql` and `0022_sync_trigger_gate.sql` (no statement changed), so a database that applied them earlier is unaffected.

### Docs

- README: a `tempad schedule` section, a `tempad scry` section, `tempad help <command>` and `backfill --from` in the command list; the Bun requirement and pin are now 1.4.2.
- The `quest` skill has a "quest created by mistake" section: retract it, do not abandon it.
- Contributors: the test suite no longer sees the developer's environment. A preload (`bunfig.toml`, repository root and `packages/core`) points `HOME` at a throwaway directory and removes every user-scoped variable (`CLAUDE_CONFIG_DIR`, `TEMPAD_*`, `ANTHROPIC_API_KEY`, `GIT_AUTHOR_*`, ...), so an exported `CLAUDE_CONFIG_DIR` no longer makes the `skill install --scope user` tests write the real `skills/tempad-quest/SKILL.md`. CLAUDE.md documents `POSITIONAL_LIMITS`, the usage-literal guard, the stint/quest id resolution, and the reclassify protections.

## [0.2.0] - 2026-10-16

### Added

- **Push sync: one history across several machines (optional).** Each machine still keeps its own `tempad.db`. With a `[sync]` section in `tempad.toml`, they all push to and pull from one self-hosted [sqld](https://github.com/tursodatabase/libsql) server. To enable it, add `[sync]` with a `url` (`libsql://`, `https://` or `wss://`; plain `http://` or `ws://` only for loopback hosts) to `TEMPAD_HOME/tempad.toml`, and put `TEMPAD_SYNC_TOKEN=<a JWT signed with the server's key>` in `TEMPAD_HOME/.env` or the environment. Plain `tempad sync` then collects, pushes and pulls; `tempad sync --push` and `--pull` (or both) run one direction only, without collecting. Without `[sync]`, tempad never opens a network connection for sync and never loads the libSQL client. Server setup (Coolify, JWT keys, backups, smoke checks) is in [`docs/deploy/sqld-coolify.md`](docs/deploy/sqld-coolify.md); the protocol and conflict rule are in `docs/specs/push-sync.md`; the README has a "Sync across machines" section. What an operator should know:
  - Events are an append-only log replayed in global `uid` order. Mirrors (GitHub, Monday, Claude sessions and messages) use last-writer-wins on `(sync_updated_at, sync_host)`, and deletes travel as tombstones. Projections are never synced: a pull that brings new events rebuilds them, and a pull that stops part-way is repaired by a durable marker on the next run.
  - `[sync].batch_size` (default 500) bounds a push or pull page; `[sync].enabled = false` turns sync off without removing the section. `[sync].url` takes no query string, fragment or `user:pass@`, and the client only ever receives a URL rebuilt from the checked parse.
  - Every host must run identical `[[projects]]` rules, because org, project and display name are synced as data.
  - A server that was lost, replaced or restored from a backup is detected and re-seeded from any one host with everything that host holds, other hosts' rows included. After restoring the server from a backup, run `DELETE FROM sync_meta WHERE key = 'server_id'` on it so every host re-seeds. A host reinstalled under the same `HOST_SLUG`, or one whose `tempad.db` was restored from an older backup, pulls its own history back instead of skipping it.
  - A host running an older tempad stops with `remote holds data from tempad schema N; upgrade tempad on this host` instead of writing into a newer database.
  - Two events with the same uid and different content are a loud error, never a silent drop.
  - `w5 backfill` and `w5 eval` classify only this host's sessions when sync is enabled, so a session pulled from another machine is never classified twice.
  - A malformed `[sync]` prints one `sync: <reason>` line and exits 1 for `tempad sync`, `w5 backfill` and `w5 eval`; it does not break commands that never sync (`w5 hook install|uninstall`, `w5 enqueue`, `w5 context`, `tempad quiet`, `tempad review`).
- **Cross-host identity merge.** Each machine ran its own `hero init`, `party add` and `client add`. When logs are combined, the first created event in uid order is canonical: one hero, one party per slug, one client per slug, one open membership per (hero, party). Later duplicates become aliases, so memberships, sagas and quests land on the canonical rows; leaving a party on one host ends only the join it names, and `tempad party leave` ends every open join. Two hosts merging a pair of quests in opposite directions cannot loop: the earlier merge in uid order wins. A single-host log records no alias and its projections are unchanged.
- `TEMPAD_SYNC_TOKEN` is a configuration variable like the others, loaded per command. Only `tempad sync` with `[sync]` enabled requires it, and `tempad setup` never prompts for it or overwrites a line you added by hand.

### Changed

- Events now carry a global `uid` (a ULID) that is the replay order instead of the local row id. Existing databases are backfilled by migration 0019 with deterministic uids, so machines that started from a copy of one `tempad.db` agree on the uids of their shared history. On a single machine the order is unchanged.
- Secrets no longer reach child processes. `MONDAY_API_TOKEN`, `TEMPAD_SYNC_TOKEN` and `GH_TOKEN` are removed from the environment of everything tempad spawns (the classifier's `claude -p`, the detached `w5 run`, `hooks/w5-common.sh`), except that the git/`gh` collector and setup's probes keep `GH_TOKEN` because `gh` reads it. Variables tempad does not own, such as `ANTHROPIC_API_KEY`, pass through.
- Every database connection now waits up to 5 seconds for a lock instead of failing at once, and opening the database no longer takes the write lock when the host slug is unchanged. Read-only commands such as `tempad report` no longer fail with `SQLITE_BUSY` while a sync, rebuild or w5 run is writing.

### Fixed

- `tempad rebuild` read the event log before taking the write lock, so an event committed by the w5 runner (or a pull) in between was missing from the projections while they were marked current. It now reads and replays inside one transaction.
- A project rule whose folder does not exist (a deleted subfolder, or a folder registered before it was created) now matches the same location reached through a symlinked parent, such as a `~/work` that points to `/work`.
- The push-sync triggers on the six mirror tables ran on every host, including hosts that never configured `[sync]`: every collected row was stamped and every deleted row left a tombstone that nothing would ever read, tripling the cost of a 20000-row insert (124 ms against 41 ms) and growing the database. The triggers now exist only once sync has run (`sync_meta('mirror_sync_enabled')`). The first `tempad sync` restamps every mirror row as written at that moment (so a row changed while sync was off is not beaten by an older version another host pushed) and installs them; with sync off, inserts, updates and deletes cost what they did before push sync, and report output is unchanged.
- The GitHub collector's reconcile step compared `gh_commits.authored_at` to the window start as text. Rows stored before commit dates were normalized to UTC keep the author's offset (`2026-09-07T23:00:00-03:00`), so one near the window boundary could be skipped and its orphaned sha (after a history rewrite) never deleted. It now compares against a UTC-normalized bound, which is valid because every stored value is UTC: migration 0021 rewrites the legacy rows, and a pull rewrites any offset-form `gh_commits` dates that older pushes left on the sync server.

### Migration

- `0019_push_sync.sql` adds the push-sync columns: `uid`, `sync_host` and `sync_dirty` on `events`, and `sync_host`, `sync_updated_at` and `sync_dirty` on the six mirror tables (`gh_repos`, `gh_commits`, `gh_pull_requests`, `monday_items`, `claude_sessions`, `claude_messages`). It also adds the triggers that stamp and dirty mirror rows and record tombstones, and the `sync_local`, `sync_cursors` and `sync_tombstones` tables. It backfills event uids on first open; nothing is sent anywhere until `[sync]` is configured.
- `0020_sync_meta.sql` adds the local `sync_meta` table, which holds the last-synced server id and the sync markers.
- `0021_normalize_commit_dates.sql` rewrites legacy offset-form `gh_commits.authored_at` and `committed_at` to UTC (`2026-09-08T02:00:00.000Z`), the form the collector writes today. Rows already in UTC are untouched, a second run changes nothing, and push-sync state (`sync_updated_at`, `sync_host`, `sync_dirty`) is left as it was.
- `0022_sync_trigger_gate.sql` drops the 18 mirror sync triggers that 0019 installs, and on a database that never synced deletes its tombstones, so a host that never configures `[sync]` pays nothing for push sync. The triggers come back on the first `tempad sync`, which also restamps every mirror row as written at that moment. A database that has already synced (non-empty `sync_meta`, a pull cursor, or anything marked pushed) keeps its triggers and every pending row, event and tombstone.

### Docs

- README: a "Sync across machines" section; the no-configuration list names `setup` (and the hidden `init` alias) and quotes the current not-set-up message.
- `docs/deploy/sqld-coolify.md`: how to self-host the sqld server on Coolify, pinned by tag and digest, with the required JWT auth, per-host tokens, backups, the restore runbook and smoke checks. An empty `SQLD_AUTH_JWT_KEY` disables auth; the page says so.
- `docs/specs/push-sync.md`: the sync design, including the audit of cross-host projection keys.
- The `quest` skill's "neither CLI exists" and "not set up" branches no longer dead-end for users without the plugin; they get the plugin route or `bun add -g @hyperlab.sh/tempad && tempad setup`. The `setup` skill finds the global bin directory with `bun pm bin -g` instead of assuming `~/.bun/bin`, and tells the user to add it to `PATH`.
