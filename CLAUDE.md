# TemPad

Reconstructs work history (hour by hour) from git, Monday.com and Claude Code session transcripts into SQLite, then generates timesheet reports.

## Layout

- `packages/core` — the npm package `@hyperlab.sh/tempad` (was `@tempad/core`): TypeScript library + `tempad` bin, schema, collectors, reports, plus the `skills/` and `hooks/` the Claude Code plugin reuses. Bun runtime, `bun:sqlite`.
- `apps/` — runnable programs. A Go TUI (charmbracelet) is planned.
- `libs/` — private bundle-time packages. Never published.
- `docs/specs/` — design specs. Read the relevant spec before changing a subsystem.

Runtime data never lives in the repo. `TEMPAD_HOME` (default `~/.tempad`) holds `.env`, `tempad.toml`, `tempad.db`, `repos/`, `reports/`.

## Commands

```sh
bun install
bun run lint          # biome check
bun run fmt           # biome + dprint write
bun run typecheck
bun test
moon run :test        # same through moon
```

## Conventions

- Package manager: bun. Never npm.
- Biome for JS/TS/JSON. dprint for Markdown/TOML/YAML. Go uses gofmt.
- Full words in identifiers (`repository`, not `repo`, in code; `repos/` as a directory name is fine).
- Environment variables that are required have no defaults; missing ones throw at startup.
- Tests in `bun test`, colocated as `*.test.ts`. Fixtures under `packages/core/test/fixtures`.
- Tests never see the developer's environment. `bunfig.toml` (root and `packages/core`) preloads `packages/core/test/preload.ts`, which calls `isolateProcessEnvironment()` (`test/isolation.ts`): `HOME` becomes a throwaway directory, every variable in `USER_SCOPED_VARIABLES` (the `ENV_VARS` table, `CLAUDE_CONFIG_DIR`, `CLAUDE_PROJECT_DIR`, `TEMPAD_*`, `ANTHROPIC_API_KEY`, `GIT_AUTHOR_*`/`GIT_COMMITTER_*`) is removed, and `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_SYSTEM` are `/dev/null` (a global `commit.gpgsign` otherwise reached every fixture commit). Subprocesses spawned with `...process.env` inherit that. A test that needs a specific `HOME`/`CLAUDE_CONFIG_DIR` uses `withEnvironment({...}, fn)` from the same file (`null` deletes), never a hand-rolled save/restore. A new `process.env` read in `src/` that names a user-scoped location or a credential must be added to `USER_SCOPED_VARIABLES`. `os.homedir()` cannot be redirected in-process (Bun reads `HOME` once at startup), so code that writes under the user's home must read `process.env.HOME`. `w5 hook install` refuses a checkout under `/tmp` (`hasUnstableInstall`); tests drive it through `runW5HookCommand(args, { hasUnstableInstall })` instead of relying on where the clone lives. Run the suite with `CLAUDE_CONFIG_DIR` pointed at an empty temp directory to prove nothing is written to it. `proto` picks Bun from `engines` inside `packages/core` (1.4.x) but from `packageManager` at the root (1.3.14); CI runs from the root.
- Tests that exercise a sliding time window (the GitHub collector reconciles only commits authored after `lastSyncAt` minus 7 days) must build fixture dates relative to `Date.now()`; absolute dates turn into time bombs once the wall clock passes them.
- Commits: `type(scope): summary`.

## CLI

- **Per-command configuration.** `loadConfig(command, needs)` (`packages/core/src/config/env.ts`) validates only the variables a command lists in `needs` and returns `Pick<Config, K> & { home }`, so a command cannot read a field it did not ask for. `ENV_VARS` in that file is the one table of every variable (name, `Config` key, description, `secret`, kind, `GH_TOKEN` optional, `TEMPAD_SYNC_TOKEN` `setup: false` with a `requiredWhen` wording); `tempad setup` reads `SETUP_VARS` (`ENV_VARS` minus `setup: false`, so it never prompts for, flags or writes the sync token, and keeps a hand-added line for it like any other it does not own) and the error messages read the table. `TEMPAD_SYNC_TOKEN` (`syncToken`) is not optional: a command that lists it in `needs` fails without it, and `tempad sync` lists it (with `hostSlug`) exactly when `[sync]` is enabled, so with no `[sync]` the token is never read; the error is `TEMPAD_SYNC_TOKEN is required when [sync] is enabled; set it in <home>/.env or the environment`. Every child process tempad spawns gets `childEnvironment(keep)` (`src/config/child-env.ts`): the parent environment minus every `secret: true` variable of `ENV_VARS` except the ones named in `keep` (the `gh`/git collector and setup's probes keep `GH_TOKEN`; the classifier's `claude -p` and the detached `w5 run` keep none), and `hooks/w5-common.sh` unsets the same three before it starts the CLI. A missing one throws `ConfigError`: `tempad sync monday needs MONDAY_API_TOKEN, MONDAY_USER; set them in ~/.tempad/.env or run /tempad:setup in Claude Code, or `tempad setup` in a terminal`. Needs: `sync monday` MONDAY_API_TOKEN, MONDAY_USER; `sync github` GH_USER, GH_ORGS, GH_INCLUDE_PERSONAL, GIT_AUTHOR_EMAILS, SINCE (GH_TOKEN optional); `sync claude` CLAUDE_DIRS, SINCE, HOST_SLUG; `sync` the union; `report *` and `w5 eval` TZ; `w5 run` CLAUDE_DIRS, HOST_SLUG (it re-syncs one session file); `scry` HOST_SLUG only when `[sync]` is enabled (own-host filtering, like `w5 backfill`); everything else none. Each collector declares its own `needs` and takes `LoadedConfig<those keys>`; reports take `LoadedConfig<"tz">`; `planW5Command` (`src/w5/cli.ts`) is the w5 equivalent. A new command that reads a config field must add it to its `needs`.
- **A `tempad.toml` value of the wrong type warns and keeps the default.** `loadIntentConfig` (`src/intent/config.ts`) reads every `[w5]` key through typed readers that call `warn(message, kind)` (`ConfigWarningKind` is `"renamed-key"` or `"wrong-type"`) instead of falling back silently: `<tomlPath>: [w5].<key> must be <expected>, got <value> (<toml type>); using the default <default>. Fix the value.` (`describeValue`, `src/config/describe-value.ts`, is the one rendering of a value and its type; every warning starts with the resolved path of the file, not the literal `tempad.toml`). Numbers are always finite (TOML allows `nan`/`inf`); counts (`watch_turns`, `ask_expire_turns`, `overlap_messages`, `memory_stints`, `memory_quests`) are safe whole numbers of 0 or more (`Number.isSafeInteger`: `1e20` is an integer to `Number.isInteger` but SQLite rejects it as a `LIMIT`, failing every window; the last three are SQL `LIMIT`s), minutes and hours are numbers of 0 or more, `timeout_seconds` is above 0 and `backfill_days` is a whole number from 1 to 3650 (what `scry --days` accepts). The default `warn` is `console.warn` (stderr, once per key per load); `tempad scry` collects them into its `config` check (`warn`, the details are the lines, the summary counts the two kinds apart) so it never prints to the console. The same applies to a non-table `[w5]` and `[[parties]]` `joined`/`description`. `loadRules(path, warn)` (`src/config/rules.ts`) covers `[[projects]]`: a non-string `name`, or an `org`/`project` of a pattern rule (a named group may supply them), warns and is ignored, while a non-string `path`/`pattern`, a path rule's `org`/`project`, an empty `path`/`pattern`, and `projects`/`repositories`/`boards` that are not arrays of tables throw. `tempad scry` calls `loadRules` right after `loadIntentConfig` (the collectors read the rules, not `loadIntentConfig`): its warnings count as wrong-type and a throw fails the config check. `[sync]` (`SyncConfigError`) and `w5 eval --declare` (`InvalidDeclareFileError`) throw on a wrong type, so they have no fallback to warn about. A new `[w5]` key goes through `count`/`amount`/`positive`/`days`/`boolean`/`string`/`parseChoice`, never a bare `typeof` ternary.
- **Configured home.** `isConfigured(home)` is true when `TEMPAD_HOME/.env` or `TEMPAD_HOME/tempad.db` exists. Any command that opens the database on an unconfigured home exits 1 with `tempad is not set up yet; run /tempad:setup in Claude Code, or `tempad setup` in a terminal` (`SETUP_HINT` in `config/env.ts`) and creates nothing; `w5 enqueue` and `w5 context` (called by hooks) exit 0 silently instead. `--help`/`-h`/`help` (and `<command> --help`), `setup` (and `init`), `--version`, `skill install` and `w5 hook install|uninstall` need no configuration and open no database, so `w5 hook uninstall` works on a machine tempad was never set up on. `tempad --help` prints to stdout and exits 0; an unknown or missing command prints usage to stderr and exits 2, and `tempad help [<command> [<subcommand> ...]]` and `<command> [<subcommand> ...] --help|-h` (the flag anywhere before a `--` terminator, at any depth: `w5 backfill --days 3 --help`, `w5 hook install -h`) print only that path's usage to stdout and exit 0, without running the command: a command lists every usage line of its own, a nested path its own line. Bare `tempad help`/`--help`/`-h` print every command plus `Run tempad help <command> for one command.`. `tempad help bogus`, `help w5 bogus` and `w5 bogus --help` exit 2 with the unknown part named and the nearest usage on stderr (`tempad bogus --help` is still exit 2). `src/usage.ts` holds both the one copy of every usage text (`USAGE_ENTRIES`; the `*_USAGE` constants of `w5 backfill`/`review`/`eval`, `scry` and `setup` derive from it through `usageText`) and `COMMAND_TREE`, the table of commands and nested paths. A new command or subcommand needs an entry in both, and in `POSITIONAL_LIMITS` (`src/usage.ts`: how many positionals each runnable path takes, so `dispatch` answers `rebuild bogus` or `sync --full bogus` with that path's usage on stderr and exit 2; `checkPositionals` skips the values of flags not in `BOOLEAN_FLAGS`, which a test checks against every `type: "boolean"` option in `src/`) (`test/cli.test.ts` walks `COMMAND_TREE`, fails on a path with no usage or one whose usage omits it, and compares the table with the paths the usage entries document)). No usage text lives outside `src/usage.ts`: every `usage:` error in `src/` prints `usageText(<path>)` or `commandUsageText(<command>)`, and a test greps `src/` for a `usage: tempad` literal and for any string literal holding a synopsis (`tempad <command>` anywhere in a line of the literal, after text or an interpolation, followed by `[` or `<`; `Usage:` in any case; comments skipped), so a hint that shows a command's syntax is built from `usageText(...)` (the hook hand-backs, `w5 review`, the setup next steps), proved against `test/fixtures/usage-literals`. Each path has its own complete entry (options included), so a usage error and `help <path>` print the same line.
- **A `.env` in the current directory is ignored.** Bun loads `./.env` by default and hooks run with the user's project as cwd. The CLI shebang is `#!/usr/bin/env -S bun --no-env-file` (honoured when run as `./src/cli.ts`, as an installed bin, and by `bunx`); `bun src/cli.ts` ignores shebang flags, so `ignoreWorkingDirectoryEnvFiles()` additionally drops any tempad variable whose value equals what a cwd `.env*` file defines. The detached `w5 run` spawn passes `--no-env-file` too. Only the caller's `process.env` and `TEMPAD_HOME/.env` count.
- `tempad setup [--non-interactive] [--home <dir>] [--force] [--no-verify] [--<variable> <value> ...]` (`packages/core/src/setup/`; `init` is a hidden alias, absent from `--help`) creates `TEMPAD_HOME` (0700) with `.env` (0600) and a commented `tempad.toml`; it needs no config and never opens the database. One flag per `ENV_VARS` entry, derived by `flagNameFor` (`MONDAY_API_TOKEN` is `--monday-api-token`, `TZ` is `--tz`), so a new variable in `ENV_VARS` becomes a prompt and a flag with no other edit. Interactive (stdin must be a TTY, else exit 1 suggesting `--non-interactive`): prompts for every variable through an injectable `Prompter` (`setup/prompt.ts`; raw-mode, secrets read with no echo, backspace works, Ctrl-C exits 130 and writes nothing); suggestions are prompt text only (system time zone, short hostname, `git config --global user.email`, `~/.claude` when `~/.claude/projects` exists (`CLAUDE_DIRS` wants the config directory, not `projects/`), `gh api user --jq .login`; all time-boxed, failures ignored), or the existing `.env` values (secrets show `(keep current)`). Non-interactive: values come from flags, then `process.env`; a missing required one exits 1 naming each variable and its flag; an existing `.env` without `--force` exits 1. Interactively an existing `.env` is only updated after a yes (lines it does not own, e.g. `ANTHROPIC_API_KEY`, are kept); `--force` replaces `.env` and `tempad.toml` without asking, leaving `.env.bak`/`tempad.toml.bak`, but lines for variables not in `ENV_VARS` (e.g. `ANTHROPIC_API_KEY`) are kept in every case and never printed; an existing `tempad.toml` is otherwise kept. Syntax checks (boolean, non-empty list, IANA `TZ`, `SINCE` as `YYYY-MM-DD`) always run; unless `--no-verify` it also checks (each time-boxed, fetch/spawn injectable) the Monday token (`{ me { id name } }`; `MONDAY_USER` mismatch only warns), GitHub (`GH_TOKEN` against `/user`, else `gh auth status`) and that every `CLAUDE_DIRS` entry exists. A network failure is "not verified": the wizard asks whether to write anyway, a non-interactive run exits 1. No secret is printed anywhere (the summary shows `set`/`not set`, and every line written is redacted of known secret values). Ends with next steps: `claude plugin install tempad@hyperlab`, `tempad hero init "<your name>"`, `tempad sync`, and `tempad w5 hook uninstall` when `~/.claude/settings.json` or `$CLAUDE_CONFIG_DIR/settings.json` holds a hook marked `"tempad": true` (`hasTempadHooks`, `src/w5/hooks.ts`). The `.env` writer quotes exactly as `parseDotEnv` unquotes, so `loadConfig` reads back what init wrote; an unset optional variable is written commented out (a blank `GH_TOKEN=` would read as an empty token).
- `tempad sync [monday|github|claude] [--full]` — `--full` clears that source's `sync_state` row before syncing, so the collector ignores the last-sync cursor and rescans everything back to `SINCE` (or, for Claude, re-reads every session file regardless of mtime). Use it to backfill columns added by a migration (e.g. `title_source`) on rows a normal incremental sync wouldn't touch.
- `tempad w5 backfill --reclassify --from <iso> [--to <iso>] [--backup <path> | --dry-run] [--model <name>]` (`src/w5/reclassify.ts`, cascade in `src/w5/reset.ts`) is the supported way to redo a range on the real database: it retracts what w5 *inferred* for the sessions in range, by `retracted` events with reason `reclassify` (nothing is deleted or edited), then classifies those sessions again from their first message with `force`. The sessions are the ones `--from`/`--to` select for plain backfill (`selectBackfillSessions`: `ended_at >= from`, `< to`, `--to` exclusive and strict ISO like `--from`), and every live trace of such a session is retracted, whatever its date, since a session is classified from its first message; then stints left with no live trace, then unconfirmed quests left with no live stint (the cascade `w5 eval`'s `resetRange` shares through `planReset`/`applyReset`: a stint or quest that keeps a live row elsewhere stays, a confirmed quest stays), and the session note of the reset sessions is cleared. `w5_windows` rows are **left**: that table is a projection of `window.classified` events, so a delete behind the log would be replayed back by `tempad rebuild` and fail `scry`'s projection check (`w5 eval` deletes them, on its throwaway copy only; `applyReset`'s `clearWindowCoverage`). The re-run uses `force`, which ignores coverage; a window that fails is not retried by a plain backfill (it counts as covered), so run the same `--reclassify` again. A session is **protected whole** (not reset, not classified, listed as `reclassify: protected <id> (<reason>)`) when it has any `quest.declared` event (`declared`), a live trace not recorded by a w5 actor (`hook`/`backfill`/`system`: `not written by w5`) or a `hero` event on one of its traces, stints or questions (`tempad answer`, a manual `stint.assigned`, `answered or assigned by a person`); an unconfirmed quest is also kept when a `hero` event ever touched it. `backfill` takes `sessionIds` (only those sessions, of the range) so it never classifies a protected session on top of what it holds. The command writes to the database, so without `--backup <path>` it exits 1 and prints a suggested `--backup` command and the equivalent `sqlite3 ... "VACUUM INTO ..."` (no recency check is possible, the flag is the proof); with it, `backupDatabase` takes a `VACUUM INTO` copy, refuses an existing file, reads it back and compares the event count, before the first write. `--dry-run` prints `reclassify (dry run): sessions=<n> protected=<n> would retract traces=<n> stints=<n> quests=<n>` plus the protected sessions and writes nothing. `--reclassify` needs `--from`, rejects `--force` and `--days`, and `--to`, `--dry-run` and `--backup` are usage errors (exit 2) without it. Re-running it retracts the previous run's rows the same way, so stints do not pile up.
- `tempad w5 backfill [--days <n> | --from <iso>] [--model <name>] [--force]` classifies the windows no trace covers. `--days` counts back from the moment of the run; `--from` is an absolute lower bound on `claude_sessions.ended_at` (strict ISO 8601 only: `YYYY-MM-DD`, or `T` datetime with seconds, optional fraction and `Z` or `±HH:MM`; `Date.parse` alone would read `1` as 2001-01-01. Normalized to ISO UTC, inclusive; any other value, an impossible date, or `--from` together with `--days` is a usage error, exit 2). `tempad scry` prints the `--from` form.
- `tempad scry [--json] [--days <n>] [--fast]` (`packages/core/src/scry/`) is the read-only data health check: Health (checks), Stats, Recommendations (each a copy-pasteable command plus a one-line reason; `RECOMMENDATION_ORDER` in `collect.ts` fixes the order), notes, timing. Exit 0 when no check failed, 1 when one did (warnings and recommendations never fail), 2 on a usage error (`scry: <reason>` plus usage on stderr); `--days` defaults to `[w5].backfill_days`. **It never goes through `openDatabase`:** `runScryCommand` opens `tempad.db` with `new Database(path, { readonly: true })` and `busy_timeout`, so it applies no migration, backfills no uid, repairs no mirror trigger and writes no host slug, and every read runs in one `BEGIN`...`ROLLBACK` snapshot. A database behind the code's schema is a failed check recommending `tempad rebuild` (which migrates); one ahead is a failed check with no recommendation. A missing database is a failed check recommending `tempad sync`. A required `scry` test checkpoints (`wal_checkpoint(TRUNCATE)`) and closes the fixture's writer, then snapshots every file of the home before and after: the main file and any `-wal` must be byte-identical, the `-shm` the same size (readers change its bytes), and a file that appears must be an empty `-wal` or the `-shm`. A readonly connection to a WAL database opens the `-shm` and `-wal` sidecars like any reader and cannot remove them on close. Whether they exist before scry runs depends on the platform and Bun version (macOS 1.4.2 leaves an empty `-wal` and a 32 KB `-shm`; Linux 1.4.2 removes both when the writer closes), so a new one is not a write; without the checkpoint, Bun 1.3.14 on macOS left 1.47 MB in the `-wal` and 4 KB in the main file, so the digest proved nothing. Network: none. `[sync]` is read for its on/off state and its url is validated with `loadSyncConfig(home, "not-read")`; `@libsql/client` is never loaded (`test/scry/cli.test.ts` runs it under `test/sync/libsql-guard.ts`). The sync section only appears when `[sync]` is enabled or the `mirror_sync_enabled` marker is set. The projection check compares every table of every registered projection with `stateAsOf(database, END_OF_TIME)` row for row over the columns both have (`scry/replay.ts`); `--fast` skips it and `quick_check`. The backfill recommendation and `backfill()` share one plan: `planBackfillWindows` (`w5/backfill.ts`) returns each window of each session (messages, bounds, previous window's end, covered or not) and `backfill()` classifies exactly its uncovered windows and counts the covered ones as `windowsSkipped`; `selectBackfillSessions` picks the sessions and `backfillWindowMinutes` (three throttle intervals) the window length, for both. There is no second copy of the message query or the coverage rule (an exact `w5_windows` row, or a non-retracted trace nested inside the window's bounds; `force` makes nothing covered), so `test/w5/backfill.test.ts` pins every boundary through real runs (window length to the millisecond, messages without text, trace bounds a millisecond off, retracted traces, `w5_windows` rows). A pending window that ended less than an hour ago is "in flight" and not counted. The printed command is `tempad w5 backfill --from <ended_at of the oldest pending session>`, an instant rather than a day count, so it covers that session however long the user waits (a `--days` count is measured from the moment of the run and went stale in between); the reason line says when in-flight windows will be classified too. The live runner never appends `window.classified`, so coverage relies on the nested-trace rule there too. `--days` accepts 1 to 3650 (larger is a usage error: `now - days` must stay a valid date). Only SQLite's own failures while opening or reading the file become a failed `database` check; any other exception is a bug and propagates. A job failing with `unknown claude session` recommends `tempad sync claude` only for sessions that are missing from `claude_sessions` and whose newest failure is strictly after the claude collector's last run (`sync_state.last_sync_at` for `claude`; no row counts as before every failure): a session whose failures all predate that run was looked for and not found, so the command could not help and would keep firing until the failures age out of the 7-day window. Those get a detail line instead ("no transcript found on disk by the last claude collection"); when every session is present now, the check says the job ran before the session was collected and the backfill covers it. The `--json` stats are `events`, `quests` (`byState`, `unconfirmed`), `stints`, `traces`, `questions`, `sources`, `collectors`, `database`, `w5`, `sync`, pinned key by key in `test/scry/scry.test.ts`. The projection compare also fails on a missing table or a missing/extra column, not only on rows. `tempad w5 eval` is only a conditional recommendation (needs at least 5 sessions with traces in the last 7 days, the range its command prints, as a baseline): the database records neither the model nor the prompts nor the `[w5]` settings behind a classification (`traces.classified_by` is the constant `assistant`), and `tempad.toml`'s mtime is no signal, so the data cannot say an eval is due. Collectors count as stale after 24 h. The `sync_meta` key constants (`SERVER_ID`, `REBUILD_PENDING`, `RESEED_PENDING`, `PULL_OWN_PENDING`, `PUSH_PROBE_EVENT`, `PUSH_PROBE_ROW`) are exported from `sync/engine.ts` so scry reads the same names. Help text and report obey the ubiquitous-language banned words (a test greps both).
- `tempad sync --forget` — the off switch for a host that leaves sync for good, local only (no network, no token). Refuses with exit 1 (`sync: --forget refused: [sync] is still enabled in tempad.toml; remove the [sync] section first`) while `isSyncEnabled(home)`, so `enabled = false` counts as removed; combined with a source, `--full`, `--push` or `--pull` it is a usage error (exit 2), as is `--force` without `--forget`. `forgetSync(database, rebuild, force)` (`src/sync/forget.ts`) first rebuilds the projections if `rebuild_pending` is set (nothing else will once sync is off; a failing rebuild throws and changes nothing), then in one `IMMEDIATE` transaction, unless nothing is left to forget (`null`), refuses with `UnpushedChangesError` (`<n> deletes / <m> changes never reached the server; ...`, printed as `sync: forget failed: ...`, exit 1) when a `sync_tombstones` row, an `events` row or a mirror row is still `sync_dirty = 1` and `--force` is not given, then deletes the `mirror_sync_enabled` marker and every `REMOTE_BOUND_META_KEYS` entry (`server_id`, `reseed_pending`, `pull_own_pending`, `push_probe_event`, `push_probe_row`; exported from `engine.ts` next to the constants, so a new remote-bound key is added in one place), clears `sync_cursors`, and calls `reconcileMirrorTriggers`, which with the marker gone drops all 18 triggers and every tombstone (the trigger list is not duplicated). The unpushed check runs only while the marker is set (`isMirrorSyncEnabled`): once a forget has dropped the triggers, new rows default to `sync_dirty = 1` with nothing to push them to, so a second `--forget` must not refuse on them. Before deleting `server_id`/`reseed_pending` it stores every distinct id of the two (they can differ) as its own `sync_meta` row `forgotten_server_id:<id>` (`forgottenServerKey`, `FORGOTTEN_SERVER_PREFIX`, `engine.ts`, value = timestamp); the rows form a growing set (forget A, use B, forget B: both are refused), are deliberately outside `REMOTE_BOUND_META_KEYS`, no forget deletes one, and `runSyncEngine` throws `ForgottenServerError` (surfaced as `sync: push failed: ...`, exit 1) right after reading the remote `server_id`, before any write to the remote beyond the idempotent bootstrap and before `enableMirrorSync` (with a forgotten id stored, that call moves from the start of the run to right after this check, so a refusal leaves the database as the forget left it), when the remote's `server_id` is in the set. Rejoining is unsafe, not idempotent: `enableMirrorSync` restamps every row as written now, so last-writer-wins would overwrite another host's later edit with this host's stale row, resurrect rows other hosts deleted, and re-send a forgotten unpushed tombstone's row. The way out is a fresh server (different id, a full seed) or an empty `tempad.db` that pulls; the deliberate override is `tempad sync --rejoin <server-id>` (`rejoinServer`, `src/sync/forget.ts`; local only, removes that one id; prints `sync: rejoin allowed for server <id>`, or, on stderr and exit 1, `sync: --rejoin: server <id> was not forgotten; nothing to rejoin`; an empty id also exits 1 (`sync: --rejoin needs a server id`), checked after the conflicting-flag checks; a usage error, exit 2, with a source, `--full`, `--push`, `--pull`, `--forget` or `--force`), named in the error. And `parseArgs` failures in `sync` (unknown flag, `--rejoin` without a value) print `sync: <reason>` plus the usage and exit 2 via `isParseArgsError` in `src/cli.ts`, the one command that does so. A refusal does not survive another host rotating the server's `server_id` (the lost-writes detection compare-and-sets a new id): the rotated id is not in the set, so this host would rejoin without noticing. `rebuild_pending` and `sync_local` stay out of that list: neither describes the remote. `sync_*` stamp columns and `sync_dirty` flags are left alone; turning sync on again against a fresh server runs `enableMirrorSync`, which restamps every row, and the missing `server_id` makes the first run an unknown server, so everything is re-sent. If a sync was running while you forgot, run `--forget` again. Prints `sync: forgot triggers=<n> tombstones=<n> cursors=<n> meta=<n>`, or `sync: nothing to forget` (exit 0) when the marker, triggers, tombstones, cursors and those keys are all already gone. `openDatabase` keeps respecting the cleared marker: `ensureMirrorTriggers` does not reinstall.
- `tempad sync --push | --pull | --push --pull` — push sync only, no collectors. Plain `tempad sync` (no source) collects, then pushes and pulls when `[sync]` is enabled. A direction flag with a source or `--full` is a usage error (exit 2); a direction flag without `[sync]` exits 1 with `sync is not configured: add [sync] to tempad.toml`. Prints exactly `sync: pushed events=<n> rows=<n> tombstones=<n> pulled events=<n> rows=<n> tombstones=<n> rebuilt=yes|no`. See "Push sync (network)" below.
- `tempad report <daily|project|hourly|weekly> --from <date> --to <date> [--org X] [--project Y] [--out path] [--as-of <iso>] [--party <slug>] [--client <slug>] [--pr-date merged|authored]` — `--pr-date` (default `merged`, `daily` only; `project` and `weekly` don't place pull requests by date) chooses which date places a pull request in a day: `merged` keeps the existing created/merged/closed behavior, `authored` places it by `gh_pull_requests.first_authored_at` (falling back to `created_at` when NULL), so work that started weeks before merge shows up on the day it actually happened.

## Intent layer

Hero, parties, clients, sagas, quests, stints, traces and questions are event-sourced: `packages/core/src/intent/`.

- **Events are append-only.** One `events` table (`packages/core/src/db/migrations/0003_events.sql`) is the source of truth; SQLite triggers reject `DELETE` and every `UPDATE` except the three sync fills (see "Push sync" below). A wrong fact is corrected by a later event, never by editing history.
- **Projections are rebuildable.** Current-state tables (`heroes`, `parties`, `memberships`, `clients`, `sagas`, `quests`, `stints`, `traces`, `trace_links`, `questions`) are plain SQLite tables derived from events by pure reducers in `src/intent/projections/*.ts`. `tempad rebuild [--until <iso>]` truncates and replays them; this is always safe to run. `rebuildAll` reads the events inside the same `IMMEDIATE` transaction that clears and replays, so an event committed by another connection can never be missed while `projection_state` is still stamped current; its `beforeCommit(database)` option runs inside that transaction just before commit (push sync clears its rebuild-pending marker there), and a throw from it rolls the whole rebuild back. Rebuilding `--until <date>` leaves the live projections showing state as of that date — the command prints `projections now reflect state as of <date>; run tempad rebuild to restore` as a reminder to re-run `tempad rebuild` with no `--until` afterward.
- **Edit intent rule.** The CLI refuses a bare edit (`saga edit` / `quest edit`) on a saga or quest that has attachments (a quest on a saga, a stint on a quest) — the caller must instead use `reword` (same id, new revision) or `replace` (new id, old one ended with `reason: "replaced"`), both of which are allowed even with attachments since they express an explicit wording- or meaning-change intent. The refusal message names the real subcommands, e.g. `saga <id> has attachments; use tempad saga reword <id> "<title>" or tempad saga replace <id> "<title>" --reason ...`. See `src/intent/edit-intent.ts`.
- **Side-quest relation.** A `quest.branched` event's subject is the side quest; it names what was left as a stint (`deviates_from`, column `quests.deviates_from_stint_id`) or as a quest (`deviates_from_quest`, column `quests.deviates_from_quest_id`, migration 0024), and the parent quest is `COALESCE(deviates_from_quest_id, <that stint's quest_id>)`. `quest declare --new ... --deviates-from <quest>` writes the quest form; `quest branch <side> --deviates-from <quest|stint> [--at <iso>]` writes whichever the id is (refusing the quest itself or a retracted one), and `--at` is how a side quest is recorded after the fact. Before 0024, `declare` wrote the event inverted (subject = parent, `deviates_from` = the new quest, at the new quest's `created_at`); events are never rewritten, so `branchRelation` (`src/intent/projections/quest.ts`) reads that signature the right way round. Migration 0024's TypeScript step (`reprojectQuests`, `src/db/database.ts`, `MIGRATION_STEPS[24]`) clears `quests` and replays every event through `questProjection.apply` alone inside the migration transaction (that reducer writes only `quests` and reads only `quests`/`identity_aliases`), so an upgraded database is repaired with no manual rebuild, including the `"undefined"` stint id an older reducer stored for a pulled new-shape event; it stamps `projection_state('quests')` as `rebuildAll` would (nothing resumes from that stamp). Any other quest id in `deviates_from` reads as the subject deviating from that quest. `deviates_from: null` (old `answer --origin current`) stores no origin.
- **Time travel.** `stateAsOf(database, until)` (`src/intent/time-travel.ts`) rebuilds projections into a fresh in-memory database from events up to a date; `saga list --as-of <iso>` and `quest list --as-of <iso>` use it to answer "what were my sagas in August".
- **Impacts.** `impact.stated` (`src/intent/projections/impact.ts`, table `impacts`) records what a change means for the client and, optionally, a theme — a fact `gh_pull_requests`/`gh_commits`/`monday_items` (pure mirrors) can never hold. Its `subject` is an evidence ref in one of four shapes: `pr:<repo full name>#<number>`, `commit:<sha>`, `monday:<item id>`, `session:<claude session id>` (a UUID; parsed/formatted by `src/intent/evidence-ref.ts`) — the fourth for work that never produces a commit or pull request (an ops session, a redesign in an unmirrored repo) and so has no other evidence ref to carry a client-facing impact line. Stating an impact for a subject that already has one is a new revision (later event wins, same as `reword`); a `retracted` event naming the stating event's id clears it. `theme` is free lowercase text (`^[a-z][a-z-]*$`); the recommended set is `feature`, `security`, `fix`, `release`, `reliability`, `process`. CLI: `tempad impact set <ref> "<text>" [--theme <t>]`, `list [--project <p>] [--from <date> --to <date>]`, `import <file.json>` (an array of `{ ref, text, theme }`). `daily.ts`/`project.ts` render a commit/PR/Monday-item line as the impact text (with a `[theme]` prefix) when one exists, falling back to the mirror's own title/subject/name; `daily.ts`'s per-session line (`<title>, HH:MM to HH:MM, N messages`) renders the impact text in place of the title the same way when one exists for `session:<id>`. `project.ts` never lists individual sessions (only per-branch/per-item rows with session counts), so it has nothing to change here. `weekly.ts` is untouched.

## w5 hook

Claude Code hooks (`Stop`, `PreCompact`, `SessionEnd`, `UserPromptSubmit`) enqueue classification jobs without ever blocking a session: `packages/core/hooks/w5-stop.sh` and `w5-prompt.sh` shell out to `tempad w5 enqueue`/`tempad w5 context` and always exit 0, logging failures to `TEMPAD_HOME/logs/w5.log` instead of surfacing them. `tempad w5 hook install|uninstall` (`src/w5/hooks.ts`) merges these into the user settings (below) or `.claude/settings.json` with `--scope project` alongside any other hooks, marking its own entries so uninstall only removes those. **One user-settings rule everywhere:** `$CLAUDE_CONFIG_DIR/settings.json` when `CLAUDE_CONFIG_DIR` is set and non-empty, else `$HOME/.claude/settings.json`, never both (Claude Code reads only one). `userClaudeDirectory`/`settingsPathFor` in `src/w5/hooks.ts` are the single TS source (`w5 hook install|uninstall`, `tempad init`'s legacy detection and `skill install --scope user`, which writes to `<that directory>/skills/tempad-quest/`); `w5_legacy_hook_installed` in `hooks/w5-common.sh` mirrors it in shell. Project scope is `./.claude/settings.json`. A settings.json that is not a JSON object makes install and uninstall exit 1 with `<path> is not valid JSON (...)` (`SettingsParseError`) and leave the file untouched. Both subcommands print the file they used (`installed tempad hooks in <path>`, `removed tempad hooks from <path>` or `no tempad hooks in <path>; nothing changed`). `install` prints `PLUGIN_RECOMMENDATION_MESSAGE` (the plugin is the recommended route) and refuses with exit 1 when this copy of tempad or its hook scripts live somewhere disposable (`isUnstableInstallPath`: a `bunx-<uid>-` directory, bun's `~/.bun/install/cache/`, or the OS temp directory), because the absolute paths it writes into settings.json would break once bun clears them; bunx users get `claude plugin install tempad@hyperlab`, and `install` is for a checkout or a global install (`bun add -g @hyperlab.sh/tempad`). `uninstall` is unaffected.

**Claude Code plugin.** The repo root is also a plugin: `.claude-plugin/plugin.json` (`name: "tempad"`, `version` kept equal to `packages/core/package.json`, `"skills": "./packages/core/skills/"`; no `marketplace.json`, that lives in `hyperlab-sh/claude-plugins`) and `hooks/hooks.json` (top-level `"hooks"` wrapper, auto-discovered, so `plugin.json` needs no `hooks` key). It registers Stop/PreCompact/SessionEnd -> `w5-stop.sh` and UserPromptSubmit -> `w5-prompt.sh` as `TEMPAD_HOOK_SOURCE=plugin bash "${CLAUDE_PLUGIN_ROOT}/packages/core/hooks/<script>"` (Stop/PreCompact/SessionEnd are `"async": true` so a cold `bun x @hyperlab.sh/tempad` download never blocks the session; UserPromptSubmit stays synchronous because its stdout is the context, timeout 10 s, Claude Code caps it at 30). Install route: `claude plugin install tempad@hyperlab`; `tempad w5 hook install` stays for checkouts and `PLUGIN_RECOMMENDATION_MESSAGE` (`src/w5/hooks.ts`) is the line it prints recommending the plugin. `claude plugin validate . [--strict]` checks the manifest; its warning about the root `CLAUDE.md` is expected.

**Install story.** Plugin route (primary): `claude plugin marketplace add hyperlab-sh/claude-plugins`, `claude plugin install tempad@hyperlab`, then `/tempad:setup` in Claude Code (`packages/core/skills/setup/SKILL.md`; it cannot run the interactive wizard, so it drives `tempad setup --non-interactive` with secrets in the environment). Optional CLI route: `bun add -g @hyperlab.sh/tempad`, `tempad setup`; `bunx @hyperlab.sh/tempad` only to try it. Other agents: `npx skills add hyperlab-sh/tempad --skill quest` (the only npx mention; the skills CLI matches the SKILL.md frontmatter `name`, and finds ours through `plugin.json`'s `skills` path). `tempad skill install` (legacy) writes the quest skill as `tempad-quest`; the hook line names `/tempad:quest` for `TEMPAD_HOOK_SOURCE=plugin` and `the tempad-quest skill` otherwise.

**Hook script order** (shared in `packages/core/hooks/w5-common.sh`, sourced by both scripts; every early exit is `exit 0` with nothing on stdout/stderr). (1) no or malformed session id; (2) `TEMPAD_HOME` is resolved with a leading `~`/`~/` expanded exactly as `tempadHome()` does (Claude settings `env` values arrive unexpanded), then not configured -- neither `TEMPAD_HOME/.env` nor `TEMPAD_HOME/tempad.db` exists -- and nothing is created, not even `~/.tempad/logs`; (3) `TEMPAD_HOOK_SOURCE=plugin` and a legacy settings hook is installed (the one user settings file by the rule above, or `$CLAUDE_PROJECT_DIR/.claude/settings.json`, matches `"tempad": true`; a stale `$HOME/.claude/settings.json` is ignored while `CLAUDE_CONFIG_DIR` is set): the plugin hook stands down so a session never gets two enqueues or two context lines; legacy hooks (no `TEMPAD_HOOK_SOURCE`) never stand down; (4) CLI resolution: `TEMPAD_BIN` (word-split, never eval), else `tempad` on `PATH`, else `bun x @hyperlab.sh/tempad` when `bun` is on `PATH`, else log one line to `w5.log` and exit 0. CLI stderr always goes to `TEMPAD_HOME/logs/w5.log`, never to the session. `w5-prompt.sh` hand-escapes its JSON output: control characters other than tab/newline are dropped (CR included), tab becomes `\t`. Tests spawn the scripts with an explicit env (temp `HOME`/`TEMPAD_HOME`/`CLAUDE_PROJECT_DIR`, `PATH=/usr/bin:/bin`) so the machine's real settings or `tempad` never leak in.

A detached `tempad w5 run` drains queued jobs: before the first it reaps jobs a dead runner left `running` (`reapStaleJobs`, `src/w5/jobs.ts`: a claim older than `JOB_LEASE_MINUTES` = 30, the same as the stale `w5.lock`, goes back to `queued`, or to `failed` with `lease expired: ...` once `w5_jobs.attempts` reaches `JOB_MAX_ATTEMPTS` = 3 or the job was requested over `JOB_MAX_REQUEUE_AGE_HOURS` = 24 ago; `claimNextJob` counts an attempt; migration 0025; the lease must exceed the classifier timeout times its one retry, so a `timeout_seconds` above 600 needs a longer one; a requeue is skipped, and the stale job failed as `superseded`, when the session already has a queued row, merging `kind`/`forced` as `enqueueJob` does; a reap-failed job's `finished_at` is its claim time, so it does not count as a recent failure; every other settle stamps the wall clock at that moment: `completeJob`/`failJob` take it as `finishedAt`/`now` and `runOnce` passes `options.clock()`, never the run's start `now`, so `finished_at - claimed_at` is the job's real duration (rows written before this fix have claimed_at = finished_at on done jobs and read as zero). `w5_runs.last_run_at` stays the run's start, which is what throttling measures from). **A job is applied once.** The lease and `w5.lock` cannot tell a dead runner from a sleeping one, so ownership is the claim: `runOnce` applies the result, closes stints, advances questions and `completeJob`s inside one IMMEDIATE transaction that first checks `holdsClaim` (state `running` and the same `claimed_at` and `attempts`, the attempt count rising on every claim even when two claims share an instant); a runner that lost it logs `discarding its result` and writes nothing, and `failJob`/`completeJob` take the claim and refuse the same way, each as ONE `UPDATE ... WHERE id = ? AND state = 'running' AND claimed_at = ? AND attempts = ?` returning whether `changes === 1` (a runner that fails after losing the claim logs `lost its claim`, not `w5 run failed`). `claimNextJob` is likewise one `UPDATE ... WHERE id = (SELECT ... queued ... LIMIT 1) AND state = 'queued' RETURNING *`, so two runners (two processes, two connections) can never both claim a row, and the claim it returns is the one the statement wrote; `closeIdleStints` runs in its own IMMEDIATE transaction that checks `holdsClaim` first (still before `buildWindow`). An error while applying rolls the job's events back. `w5.lock` (`src/w5/lock.ts`) holds the runner's pid, is taken with `acquireLock` (`openSync(..., "wx")`, O_EXCL, so of two runners spawned together exactly one wins; the `--detached` parent only checks it exists and leaves taking it to the child), is removed by `releaseLock` only while it still holds that runner's own pid (another runner may have cleared it as stale and taken its own), and is stale only when untouched for `STALE_LOCK_MINUTES` and that pid is not running, or past `LOCK_MAX_HOLD_HOURS` (6) whatever the pid says (a reused pid), and a lock that vanishes while it is being checked or cleared (`ENOENT`) counts as no lock; clearing a stale lock is check-then-unlink, so two runners can both clear it, which is harmless because the lock only avoids duplicate work and the claim is what keeps a job from running twice; the log line names which rule fired (`its runner is not running`, `no pid in it`, or the hold ceiling); `runOnce` calls `beforeJob`, which touches the lock, before each job; for each job it re-syncs the one session file, and a session not yet in `claude_sessions` (the hook beat `sync claude`) is first located by `findSessionTranscript` (`src/collect/claude.ts`: `projects/*/<id>.jsonl` under `CLAUDE_DIRS`, id restricted to `[A-Za-z0-9_-]`) and collected, so only a session with no transcript on disk fails as `unknown claude session: <id> (no transcript found ...)`; no retry or backoff, because the cause is not timing and nothing would wake a deferred job. Then it builds a window of messages since the last run (`src/w5/window.ts`), classifies it, and applies the result as intent events (`src/w5/apply.ts`) — reusing or opening stints, proposing unconfirmed quests, branching on a detected switch. `src/w5/questions.ts` runs the hand-back rules: a question watches for `watchTurns` turns before it's asked, `why` questions on a stint that already has a quest expire straight to `tempad review` instead of asking, and an ask budget plus `tempad quiet <2h|30m>` keep it from asking too often.

**Classifier backend.** `[w5].backend` in `tempad.toml` is `"claude-cli"` (default) or `"api"`. `"claude-cli"` (`src/w5/classifier-cli.ts`, `ClaudeCliClassifier`) shells out to the local `claude -p` CLI in print mode with `--safe-mode --no-session-persistence --output-format json --tools ""`, prompt on stdin, cwd forced to `TEMPAD_HOME` (never the repo — no project `CLAUDE.md` or hooks leak in), so classification rides the operator's Claude subscription and never needs `ANTHROPIC_API_KEY`. `[w5].claude_command` overrides the binary name/path (default `"claude"`). `[w5].timeout_seconds` (default `180`) bounds a single classify request for both backends — the CLI backend kills the child process and the API backend aborts the fetch after this many seconds; `tempad w5 backfill` retries a window once on any classify failure (on top of the classifier's own JSON retry) before counting it failed. `"api"` (`src/w5/classifier.ts`, `AnthropicClassifier`) keeps the original behavior: POSTs to the Anthropic Messages API and requires `ANTHROPIC_API_KEY`. Both backends share the JSON-extraction/validate/retry-once loop in `src/w5/classifier-shared.ts`. `ANTHROPIC_API_KEY` is read by `anthropicApiKey(home)` (`src/config/env.ts`): the real environment first, then `TEMPAD_HOME/.env`, no default; it is only ever required when the backend is `"api"`; `loadConfig` never requires it, so hooks run fine without it (they just log and no-op) and the default `claude-cli` backend never touches it.

**Backfill order.** Sessions are read ordered by `started_at` ascending, and every (session, chunk) pair is collected into one list sorted by chunk start, then classified in that order -- windows run chronologically **across** sessions, not one session to its end before the next begins. Two sessions running the same afternoon interleave in real time, and processing them session-by-session showed a window work that, from its own point in time, had not happened yet. Each session's per-chunk `sinceTs` chain still holds: a chunk's overlap tail comes from its own session's previous chunk, never from whichever window happened to run just before it.

**Backfill resilience.** `tempad w5 backfill` (`src/w5/backfill.ts`) classifies each session's windows independently: a window that throws (after one retry) is logged as `backfill: failed <session> window <n>: <message>`, counted in `failed`, and does not stop the rest of that session or later sessions. The "already covered" check queries an explicit `w5_windows` table (`session_id, started_at, ended_at`), populated by a `window.classified` event appended right after a chunk is successfully applied (`src/intent/projections/window.ts`) -- not by looking at the traces a chunk produced, since a chunk the classifier splits into 2+ segments yields 2+ traces, none of which individually spans the chunk's exact bounds. A session partially processed by a crashed run only has its actually-classified windows skipped; the rest are (re)classified on the next run, so a crash never causes silent gaps or duplicate windows. Windows skipped this way are counted in `windowsSkipped`. The command exits 0 as long as at least one window was classified, and 1 only when every attempted window failed; the summary line is `classified=<sessions> windows=<succeeded> failed=<failed> skipped=<sessions already covered> windows_skipped=<windows already covered>`.

**Declared quests.** `[w5].mode` (`"declared"`, default, or `"inferred"`) switches the classifier between verifying a session's own declared quests (`tempad quest declare`, the `quest` skill, `/tempad:quest` in the plugin) and today's inference behavior; `[w5].inference_fallback` (default `true`) lets a session that never declares anything fall back to inference during backfill. See `docs/specs/2026-09-07-declared-quests-design.md` and `docs/specs/2026-09-07-stints-design.md`.

**Two prompts, one per mode.** `buildSystemPrompt(mode)`/`buildUserPrompt(window)` render the verifier schema (`belongs`/`guess`, `quest`/`stint`, the active quests with their plans, stint aliases) in declared mode and the pre-verifier schema (`matchedQuest`/`proposedQuest`/`questions`, open quests, recent side quests, real stint ids) in inference mode; `ClassifierWindow.mode` carries the choice from `buildWindow` to both classifiers, and `validateResult` keys off it too — inference-mode segments have no `belongs` field and their selectors are not alias-checked. The inference path's `apply.ts` reads `matchedQuest`/`proposedQuest`, so rendering the verifier prompt there would leave every quest unresolved and silently defeat `inference_fallback`. Both fixed prompts stay under 2 KB. Fakes that hand-return a `ClassifierResult` bypass both functions, so the per-mode rendering has its own tests.

**Verifier mode.** In declared mode the classifier never chooses a quest — it verifies. `ClassifierWindow` carries `activeQuests`/`activeQuestAliases`, `parentActiveQuests`/`parentActiveQuestAliases` (a subagent's parent), `openStintAliases` and `planAliases`; `openQuests`/`recentSideQuests` are built only in inference mode, so declared-mode windows have no quest lists at all. Each `ClassifierSegment` answers `belongs` (does this stretch serve one of the active quests) with a `guess` naming what it looks like instead — required when `belongs` is false, forced back to `null` when it is true — plus `quest` (which active quest it serves) and `stint` (where it lands). `matchedQuest`/`proposedQuest` remain on the type but are inference-only.

**A session accumulates declarations.** Every `tempad quest declare` marks its quest **active** for the session from that moment on; declaring a second quest no longer retires the first. `activeDeclaredQuests(database, { sessionId, at })` (`src/intent/declarations.ts`) folds the session's `quest.declared` events in order — a plain declaration adds or amends a quest's plan, one carrying `done: true` removes it — and returns the survivors oldest-first with fresh `Q1..Qn` aliases (assigned per call over the surviving set, never persisted). `tempad quest declare --session <id> --done <quest>` writes that ending event; `--done` is mutually exclusive with `--quest`/`--new`/`--plan`/`--origin`, and naming a quest that is not currently active exits 1 rather than appending an event that changes nothing. `activeDeclaredQuests` takes an optional `scope` (default `"session"`); `"subagent"` also needs `parentSessionId`, since a subagent's declarations are keyed by the pair. `--done` with `--parent` checks and ends the subagent-scoped declaration, matching the scope the event is written in. `currentDeclaredQuest` is untouched and still resolves the single latest declaration for the callers that only want one (`report/intent-queries.ts`'s non-Claude attribution). The hook context line (`buildDeclarationLine`, `w5/hooks.ts`) now reads `active quests: <title> [Q1], <title> [Q2]` — or `none` — and the `belongs` hand-back lists the same set, since a doubt is raised against all of them at once.

**The plan defines the grain.** A declaration's `--plan` is the list of **stints** the verifier matches against before it may propose a new one, never a list of maneuvers ("read the brief; edit the file; run tests" is one stint, not three). The prompt lists each active quest's plan as `P<n>.<m>` (numbered per quest: `Q2`'s items are `P2.1`, `P2.2`) alongside the session's open stints as `S1..Sn`. A segment's `stint` is one string with a structural prefix — `P2.1`, `S1`, or `new: <one line>` — rather than three optional fields, because the candidates now come from two different sources that the value itself has to disambiguate. A plan item is prompt-only until a segment names it: `apply.ts` then opens one stint for that (quest, plan item) carrying `plan_index` plus `plan_item`, the plan line's text at that index (`stints.plan_index`/`plan_item`, migration `0013_plan_stints.sql`), and reuses it for every later segment naming the same pair, in this window via an in-memory map and across windows via a lookup. Reuse is keyed on `(session, quest, plan_item)` — the plan line's text, never the alias, which is stored for display and audit only. Plan numbering is assigned fresh every window, so an insertion ahead of an unfinished item moves it from `P1.1` to `P1.2` while naming the same outcome: keying on the alias would open a second stint for work already in flight and split its traces. Changing the _text_ is the real amendment, and that correctly finds nothing to reuse — it opens its own stint and leaves the old one untouched. A stint belongs to the session its traces do (`stints` has no session column), which is how `buildWindow` scopes its candidate slice too; coming back after it closed opens a stint that `continues` it. The latest plan declared for a quest in the session wins, since `activeDeclaredQuests` keeps amending each quest's stored plan.

**Reports and eval on dismissal.** Beyond the exclusions "Stint lifecycle" (below) already lists, `daily.ts`'s per-quest rendering gains a sibling "short work" line summing dismissed-stint trace minutes per quest (nothing renders when a quest has none), and `w5 eval` prints `stints_dismissed=`/`plan_stints_hit=`/`stints_new=` alongside its existing metrics — segments landing on a plan item, and stints opened outside the plan, respectively. `weekly.ts` has no per-quest section (its table is per-day/per-project), so its equivalent is a `short work` column summing the same dismissed-stint minutes per project rather than per quest. See `docs/specs/2026-09-07-stints-design.md`.

**Aliases.** Declared-mode windows label candidate stints `S1..Sn` in list order (session-open first, then recent) and return `openStintAliases` as the reverse map; active quests are `Q1..Qn` (`activeQuestAliases`) and a subagent additionally sees its parent's as `PQ1..PQn` (`parentActiveQuestAliases`), which is a valid target for `segment.quest` since the two prefixes never collide. The prompt never contains a ULID, which closes the "garbled 26-character id" failure mode by construction. `validateSegment` repairs anything the window never offered rather than rejecting the window: an unknown `stint` selector becomes `"new: <what>"`, and an unknown `quest` alias forces `belongs: false` with a default `guess` of `"unrecognized quest alias"` so the doubt still reaches a human — both count the existing `selectorDefaulted`, since they are the same "the model named something not on the list" failure. `apply.ts` maps aliases back before touching a row. Inference mode keeps real ids in the slice, since its `apply.ts` path looks them up directly.

**`validateResult` repairs what a formatting slip would otherwise turn into a lost window, and counts each repair** (`ClassifierResult.overlapDropped`/`boundsClamped`/`guessDefaulted`/`sessionNoteTruncated`, summed by `backfill` and printed by `w5 eval` as `overlap_dropped=`, `bounds_clamped=`, `guess_defaulted=`, `session_note_truncated=`). Timestamps (`repairBounds`, run before the segments are validated, only when the window has messages): a segment that ends before the window's first message lies wholly in the overlap tail, which is context only, and is dropped (`overlapDropped`; `apply.ts` no longer has its own overlap check, so there is one place); one that starts in the tail is clamped to the first message, and one that ends after the last message to the last (`boundsClamped`). Comparison is on instants (`Date.parse` of strict ISO 8601 with `Z` or an offset), not text, so `12:05-03:00` is 15:05Z, and every well-formed pair `repairBounds` keeps is rewritten to canonical UTC (`toISOString`) so `validateSegment`'s text comparison and the stored traces see the same instant (`15:30:00Z` equals a message at `15:30:00.000Z`). Clamping that leaves no time (`start >= end` after the clamp: a tail segment ending exactly on the first message, or one starting on the last message and running past it) drops the segment (`overlapDropped`), since a zero-minute trace is noise; a zero-length segment the model sent that needs no clamping is kept. A start after the last message, an inverted pair (`start > end`), a timestamp that does not parse and one that is not a string are left alone by `repairBounds` and still a validation error with a retry hint from `validateSegment`: there is no span to keep. A result whose segments were all dropped is valid and empty. `sessionNote` over 300 characters is cut to 299 plus `…` (`sessionNoteTruncated`; `cutAtCodePoint` steps one back rather than split a surrogate pair, and the 500-character response excerpt uses it too), since it is a hint for the next run; a non-string is still an error. `belongs: false` with an empty, missing or non-string `guess` gets `UNSPECIFIED_GUESS` (`"something else"`, `guessDefaulted`) so the doubt still reaches `tempad review` and the `belongs` question, whose hand-back already renders a guess. **A failed job keeps the start of the rejected response.** `classifyWithRetry` throws `ClassifierResponseError` carrying the second response's text, and `runOnce` stores `<message>\n--- response (start) ---\n<first 500 characters>` in `w5_jobs.error` (`describeJobFailure`, `RESPONSE_EXCERPT_MARKER`, `src/w5/classifier-shared.ts`), with no new column; the log line stays the message alone. `tempad scry` groups failures by the message before the marker (`failureMessage`), so a response excerpt never splits a group, and the `unknown claude session%` match is unaffected because it anchors on the start of `error`.

**A missing or unrecognized `quest` is repaired, never a validation failure that drops a `belongs: true` segment.** When the session (plus parent) has exactly one active quest, `validateSegment` silently assigns that quest to a `belongs: true` segment whose `quest` is missing, null, or an alias the window never offered (`DeclaredAliases.soleQuest`) — no doubt, no `selectorDefaulted`, since there is only one thing the model could have meant. With two or more active quests there is no such single default: a missing `quest` is repaired exactly like an unrecognized alias — `belongs: false`, a `guess` of `"unrecognized quest alias"` or, for a missing one, `"quest not named"` (`QUEST_NOT_NAMED_GUESS`) — counting `selectorDefaulted`, never failing the window. Zero active quests (nothing declared yet, declared only after the window, every declared quest ended with `--done` or retracted) is repaired too, and it was the cause of every `expected an active quest alias` failure on the live database: there is nothing to belong to, so a `belongs: true` segment whose `quest` is missing, null or any string has its `quest` dropped to `null` (`belongs` stays `true`, no `guess`, no doubt), counting `selectorDefaulted`. A doubt here would be wrong: `needsDeclaration` already records the window's traces with no quest and asks to declare once for the whole window rather than per segment. A model's explicit `belongs: false` in such a window is left alone. This was the Sep 2 eval's biggest failure mode: 10 of 18 failed windows were exactly `segments[N].quest: expected an active quest alias when belongs is true` on sessions with one active quest.

**Doubts and the two question kinds.** `AppliedSummary.questConflicts` and `BackfillResult.questConflicts` are both named `doubts` (and `w5 eval` prints `doubts=`); in declared mode it counts `belongs: false` segments, in inference mode the old quest disagreement — a run is one mode or the other, so the two meanings never coexist. `QuestionKind` is `"belongs" | "declare"`. A `belongs: false` segment records a doubt (even when asking is disabled, so backfill and `tempad review` still show it) and, when asking is on, asks a `belongs` question carrying the segment's `guess` in the `questions.guess` column (`0010_verifier_questions.sql`). A declared session with nothing declared _yet_ records its traces with `quest_id = null` and asks exactly one `declare` question for the whole window, once its undeclared segment time reaches `[w5].stint_min_minutes` (as premature as a stint would be, `declarationDue` in `apply.ts`) — an undeclared window is one gap, not N. In a subagent session both questions are addressed to the parent session, which is the one that can answer. Hand-back sentences are rendered fresh at read time by `buildBelongsHandback`/`buildDeclareHandback` (`w5/hooks.ts`) from kind + guess + the quests active _now_ (listed with their `Q` aliases), never from the stored `text`, which is internal for these two kinds; `w5 context` and `tempad review` both render them, so an expired doubt stays answerable. `tempad answer` takes exactly one of `--belongs` (confirms the quest, moves nothing) or `--quest`, the latter optionally with `--origin current --trigger ... --kind ...` to record the side quest the answer reveals.

**A `declare` question dies with the declaration.** The question is queued while the session has declared nothing and watched for `watch_turns` turns, so the declaration usually lands before it is asked (or while it is asked). `sessionHasActiveDeclaration` (`src/intent/declarations.ts`) is the one answer to "does this session have a declared quest": it resolves the way `buildWindow` does when it decides a window needs a `declare` question -- the parent id from the session's latest declaration (`latestDeclaredParentSessionId`, shared by `window.ts` and `apply.ts`) first, then the subagent's own quest or the parent's active ones, or a plain session's `activeDeclaredQuests`. `advanceQuestions` resolves every watching or asked `declare` question of a session (`question.answered`, `answeredBy: "context"`) as soon as it is true, and `w5 context` skips the hand-back on it, so a question never reaches a session that has declared. A quest ended with `--done` or retracted is not active, so there the question stands and the hook may still say "no declared quest". Two renderings deliberately differ: the hook's `active quests:` line is the session-scope fold only, so a subagent that declared with `--parent` shows `none` there while its `declare` question is already gone; and `tempad review`, which looks back at sessions that may long since have ended their quests, hides an expired `declare` question when the session (or its parent) ever declared a quest that is not retracted (`sessionEverDeclared`), `--done` included. `hasAnyDeclaration` counts retracted quests and must not be used for either.

**Doubts are recorded on the trace itself, not only on a question.** `recordTrace`'s `TraceInput` (`intent/api.ts`) carries optional `belongs`/`guess`, forwarded into the `trace.recorded` payload in declared mode; the `stints` projection (migration `0014_doubt_traces.sql`, mirrored in its `CREATE TABLE traces`) stores the guess in a `doubt TEXT` column, null when the segment belonged. `apply.ts` logs one line per doubt regardless of whether asking is enabled -- `w5 doubt: session <id> stint <id> guess "<guess>"` -- and `tempad review` lists every trace with a non-null `doubt` in the last `N` days (`--days`, default 7), even one that never got a question asked about it. `w5 eval` prints `doubts_recorded=` from the copy, counted straight off `traces.doubt`, so the fact is auditable independent of the ask budget and quiet windows that gate `doubts_answered`.

**`new:` reuses a stint by outcome text before opening a fresh one.** A `new: <outcome>` selector used to always open a new stint, even when the classifier had already opened one with the identical outcome earlier in the same session under a different window -- the Sep 2 eval saw the same duplicate-screenshots outcome opened as a `new:` stint up to 5 times in one session. `resolveStintForSegmentDeclared` now checks, in order: an open stint of the session whose `outcome` equals the selector's trimmed text is reused exactly as an `S<n>` selector would (attaching the quest only if the stint has none, never reassigning); failing that, a closed, non-dismissed stint of the session with the same outcome opens a new stint `continues`-linked to it, exactly like the `S<n>`-on-a-closed-stint case; only when neither matches does it open a genuinely fresh stint. Matching is on `outcome` text alone, scoped to the session via the same `EXISTS (... traces ... session_id = ?)` join the plan-item reuse query uses.

**Nothing is inferred in declared mode.** `applyResult` never appends `quest.created`, `quest.branched` or an `stint.assigned` that reassigns a matched stint's quest; the declared quest is attached only to a stint that has none. `resolveQuest`/`createQuest`/`branchQuest` stay in `apply.ts` for the inference path and are simply not called from the declared one. The per-session fallback decision is made once, before backfill's chunk loop: a session that declares nothing _ever_ runs inference (its quests get `origin_kind: "inferred"`), while a session that declares partway through runs declared for its whole span — its earlier chunks take the `declare`-question path. That per-session rule is exactly what keeps inferred quests off a declared session's stints. A live `runOnce` never falls back: `inference_fallback` is backfill's alone.

**Retractions.** Events are append-only, so a wrong or duplicate fact is corrected by a later `retracted` event, never by editing history. A `retracted` event's `subject` is the id of the row it retracts (a trace, stint, or quest id) and its `payload` carries `{ retracts: <event id>, reason }`; the `stints` and `quests` projections (`src/intent/projections/stint.ts`, `quest.ts`) each try an `UPDATE ... SET retracted_at = ? WHERE id = ?` for the tables they own, so exactly one table's row is ever touched per retraction. Reports (`src/report/intent-queries.ts`) and `tempad review`/`w5 review` filter `retracted_at IS NULL` throughout, so a retracted trace/stint/quest disappears from minutes, evidence, and review output without its history being erased.

**`tempad w5 dedupe [--dry-run]`** (`src/w5/dedupe.ts`) is the fix for the backfill duplication incident: it groups live traces by `(session_id, started_at, ended_at)`, keeps the earliest (lowest event id) trace in each duplicate group, and retracts the rest with reason `duplicate backfill window`. It then retracts stints left with no live trace and unconfirmed quests left with no live stint, both with reason `orphaned by dedupe`, cascading through whatever the trace retraction orphaned (e.g. a whole second stint/quest opened by a re-run of the same window). `--dry-run` computes and prints the same counts without writing. Safe to run repeatedly -- a clean database dedupes to `traces=0 stints=0 quests=0`.

**Stint lifecycle.** TemPad tracks the attention of the human, not of the agent: one session (a team lead coordinating two quests, a session running parallel subagents) legitimately holds several stints open at once, so they interleave rather than exclude each other. A `stint.closed` event's payload carries a `reason` (`"idle" | "session_end" | "switch"`), stored as `stints.close_reason`: `reason` says why the stint stopped being open. (A close-time `outcome` judgment column existed before the 2026-09-07 rename but was never written; migration 0011 dropped it, and `stints.outcome` now holds what the stint pursued.) `switch` stays in the enum and projection for events emitted before this change, but nothing emits it anymore — a switch closes nothing. `src/w5/lifecycle.ts` emits the two reasons still in use: `closeIdleStints` closes any open stint of a session whose last trace ended more than `[w5].stint_idle_minutes` (default 45) minutes before the current run's window starts, before classification ever sees it; `closeSessionStints` closes every remaining open stint of a session and clears `w5_runs.session_note` when the `SessionEnd` hook fires. `openStintContinuing` opens a new stint with an optional `continues: <closed stint id>` link, recorded in the `stints.continues` column, for returning to the same outcome after a gap, and optional `planIndex`/`planItem` recorded as `stints.plan_index`/`plan_item` when the stint stands for a plan item. A stint closed by either path is then checked against `[w5].stint_min_minutes` (default 5): if its live trace minutes are below the minimum, `closeIdleStints`/`closeSessionStints` append `stint.dismissed` (reason `"below minimum"`), recorded as `stints.dismissed_at`. A dismissed stint's traces are not retracted or reassigned — they keep their `stint_id` and quest — but the stint itself is excluded from report/eval queries, the classifier's memory slice, and stint selection everywhere else (`dismissed_at IS NULL` alongside `retracted_at IS NULL`). `isSwitch` on a segment only marks the nexus event for side-quest branching in `apply.ts` (`quest.branched`, `deviates_from` = the previous segment's stint, `kind` one of `blocker | curiosity | waiting | unknown`) — appended only when the segment's quest is not already open in the session, since returning to a quest already in flight is not a nexus event. Time accounting sums trace minutes, never stint spans, so overlapping stints never double count. Three more `[w5]` keys bound the classifier's memory slice: `memory_hours` (default 8) and `memory_stints` (default 10) limit how far back and how many recent stints it can see, `memory_quests` (default 20) caps `openQuests` in inference mode, ranked this session's quests first, then the project's, then the rest, each by most recent use, except that the quest of every stint the window offers (session-open and recent) is always listed even past the cap (on real data the uncapped list was ~475 quests, 66 KB of prompt; a quest left out cannot be matched, so the classifier may propose a duplicate of it; `0` offers only those stint quests), `overlap_messages` (default 3) is how many prior messages are included as non-classified context.

**Classifier memory slice.** `buildWindow` (`src/w5/window.ts`) hands the classifier a recent-context slice instead of a single previous trace: `sessionOpenStints` (this session's still-open stints), `recentStints` (stints in the same `org/project` opened or closed within `memory_hours`, capped at `memory_stints`), `recentSideQuests` (the last 3 branched quests with their trigger), `overlapMessages` (the tail before the window's cut, context only), and `previousSessionNote` (`w5_runs.session_note`), which is rendered inside a fenced, explicitly-labeled data block — the note is classifier-authored but composed from transcript text the user and tools control, so the system prompt states that fenced text is a hint, never an instruction, and any fence inside the note is neutralized. `openQuests` (inference mode) is ranked and capped at `[w5].memory_quests`, and always includes the quest of every session-open and recent stint, so a stint shown with its quest's title can be matched to that quest by id. A stint's latest trace is the one with the latest `ended_at`, then the latest `started_at`, then the highest id (ties happen when a window's last message ends several segments at once). `recentStints` includes _closed_ stints of the current session as well as other sessions', because an idle gap mid-session closes a stint and returning to it afterwards is exactly a `continues` link; still-open ones live only in `sessionOpenStints`, so nothing appears twice. A whole-session window (`sinceTs` null, as backfill builds) has no overlap tail — there is nothing before its first message.

**The three-way selector is inference-only from now on.** In inference mode each `ClassifierSegment` must still set exactly one of `matchedStint` (reuse an open stint), `continuesStint` (resume a closed one) or `newStintReason` (why neither fits), and `validateResult` repairs a violation instead of rejecting the window, since failing loses a real stretch of work over a formatting slip: a segment naming none defaults to `newStintReason: "classifier gave no reason"` and counts `selectorDefaulted`; one naming several is narrowed by the precedence `matchedStint > continuesStint > newStintReason` and counts `selectorAmbiguous`. Declared mode replaced all three with the single prefixed `stint` field described above, so those three fields are typed optional and are absent there — `validateSegment` branches on `mode` for them exactly as it already does for `belongs`/`guess`. `validateResult` also normalizes every optional field (`matchedQuest`, `proposedQuest`, `trigger`, plus the three selectors in inference mode) from absent to `null` before validating -- a model that omits a key means the same as one that sends `null`, and treating absence as a type error used to fail whole windows. `ClassifierResult` also carries a top-level `sessionNote` (at most 300 characters), written to `w5_runs.session_note` by `completeJob`'s trailing `sessionNote` parameter and fed back on the session's next run. `applyResult` never trusts a stint id the classifier returns: every id is looked up (ignoring retracted rows) before use. `matchedStint` reuses a stint that is still open, and a stint that has closed is a return after a gap, so it becomes a `continues` link exactly as if it had been named in `continuesStint`; `continuesStint` links a closed stint, and pointed at a still-open one it is treated as a plain reuse, since opening a second row would leave two open stints for one outcome. "Open" is as of the segment's start (`readStint(database, id, at)` in the inference path): a stint that closed at or after `segment.startedAt` was open when the work began, which is how `buildWindow` offered it when later windows were already classified (`--force`, `--reclassify`), so it is reused rather than continued by a new stint overlapping it. The declared path still reads a stint's current state. An id that resolves to no live stint falls through to opening a new stint and counts an `unknownStintIds`. **A quest id in a stint slot (and a stint id in `matchedQuest`) is repaired before any of that** (`normalizeInferredSelectors`, `src/w5/apply.ts`, inference mode only; declared mode never calls it): the inference prompt lists quests and stints by ULID side by side and the 2026-10-18 backfill logged 345 `w5 unknown stint id` lines, 236 of them naming a quest and 91 a closed stint, each opening an unlinked stint per window. Every repaired id is resolved against the window's own candidate lists only (`sessionOpenStints`, `recentStints`, `openQuests`: already bounded by `windowEnd` and filtered by state), never the database, so a repair cannot reach a stint opened after the segment, an abandoned or merged quest, or another session's open stint (the lists are as of `windowEnd`: a stint that closed at or after it is offered as open, a quest's state, merge and retraction are judged from the events up to it, a quest must exist by it, and a stint's latest trace is the latest before it); an id outside the lists (a garbled one) stays unknown. A quest named in `matchedStint`/`continuesStint` reuses this session's open stint of that quest, else continues its latest closed one in `recentStints` (the project's, so possibly another session's), else opens a new stint, and becomes `matchedQuest` when none was given; when `matchedQuest` names a different quest it wins and the stint slot is dropped (no cross-quest `continues`). A stint named in `matchedQuest` stands for that stint's quest, so the conflict check against `matchedStint` still runs; it is promoted to the stint selector only when the segment named none and `newStintReason` is the defaulted `DEFAULT_NEW_STINT_REASON`, and only for this session's open stint or a closed one. A stint named in `matchedQuest` stands in for its quest only while that quest is an open candidate. A repaired segment's confidence is capped at 0.5 (bookkeeping only: the low-confidence list uses `< 0.5` and nothing else reads it), it counts in `selectorRepaired` (`AppliedSummary`, `BackfillResult`, `w5 eval`'s `selector_repaired=`) and logs one `w5 stint selector repaired: ...` line per repair. `applyResult` also never reassigns a matched stint's quest, but only a real disagreement counts: a `questConflict` needs `matchedQuest` to be a **non-null** id different from the stint's own. `matchedQuest: null` is _no opinion_, not "no quest" -- the stint keeps its quest and nothing is reported, without which nearly every segment counted as a conflict. A matched stint's quest changes only to fill a gap, never to settle a contest: `proposedQuest` on a matched stint that has **no** quest creates it and attaches it through the ordinary `stint.assigned` path, counting `questProposedOnMatched`, and a non-null `matchedQuest` on a stint with **no** quest attaches that quest the same way, counting `questAttachedOnMatched` (`w5 eval`'s `quest_attached_on_matched=`), but only when it is one of the window's `openQuests` and the stint is one of this session's `sessionOpenStints` (an id outside the list, another session's stint or one the window never offered stays a doubt, and a stint that already has another quest keeps it). Traces take their quest from their stint, so one segment's `matchedQuest` puts every earlier trace of that stint under the quest; that is why it is limited to this session's stints. Before, such a stint stayed quest-less, counted a doubt every window and left its traces unattributed. The summary carries `doubts` (`questConflicts` before the verifier landed), `unknownStintIds`, `questProposedOnMatched` and `questAttachedOnMatched`. Everything in this paragraph from `matchedQuest` onward describes the **inference** path only; declared mode makes no quest decision at all.

`buildWindow` takes a `windowEnd` -- the last message timestamp of the window being classified -- and every candidate is bounded by it: a recent or session-open stint must have `opened_at < windowEnd`, and a recent one must also still be open or have closed within `memory_hours`. Backfill walks history, so without this bound a window on Sept 1 was offered stints opened on Sept 3 by a session processed earlier; the classifier matched them, the traces it recorded landed before their stint's `opened_at` (negative measured durations), and `continues` could almost never fire. A live run passes `now`, for which the bound is a no-op -- nothing in the database is in its future.

Relatedly, a stint's `opened_at` is the **segment's** `startedAt`, not the run's wall clock: backfill classifies history with `now` set to the moment the run happens, and stamping `opened_at` with that put every backfilled stint days after the traces it owns.

Backfill rebuilds the slice **per chunk**, not once per session: chunk n+1 must see the stints chunk n opened or closed and the note it wrote, exactly as a live run sees the previous hook invocation's work. Its `sinceTs` is the previous chunk's last message so the overlap tail is the messages before the chunk, never the chunk's own — `messages` is then overridden with the chunk. `writeSessionNote` (`src/w5/jobs.ts`) is the shared note write used by both backfill's per-chunk loop and the runner's `completeJob`.

Ordering matters in `runOnce` (`src/w5/runner.ts`): `closeIdleStints` runs **before** `buildWindow`, so the slice never offers a stint that idleness already ended — the window's start comes from a direct `MIN(ts)` query rather than the built window.

**`tempad w5 eval --from <date> --to <date> [--db <path>] [--declare <file>]`** (`src/w5/eval.ts`) measures the stints/traces ratio against real history without ever writing to the real database: `--from`/`--to` are validated as parseable dates with `from <= to` (rejecting bad input with a message and exit 1) before anything touches disk. `validateEvalRange` then normalizes both into an exclusive-`to` range (`normalizeEvalRange`): a bare date (`"2026-09-02"`, no time component) resolves to that day in the configured `TZ` (via `localDayBoundsUtc`, the same helper reports use) — `from` becomes that local day's UTC start and `to` becomes the _next_ local day's UTC start; a full ISO input is trusted as given. `w5 eval` also prints `sessions_declared=`/`sessions_inferred=` (from `backfill`'s per-session `modeFor`), so a mixed declared/inferred run is no longer invisible. Every downstream comparison on the upper bound uses strict `<` against this normalized `to` (in both `eval.ts` and `backfill.ts`), so a bare `--to 2026-09-02` reads as "through the end of Sept 2", not "through Sept 2 at midnight" — a bare date compared with `<=` as TEXT against full ISO timestamps would otherwise silently exclude the entire `to` day, since any timestamp on that day sorts lexicographically after the bare date string. The source (`--db`, else `TEMPAD_HOME/tempad.db`) is copied to `TEMPAD_HOME/scratch/eval-<timestamp>.db` via SQLite's own `VACUUM INTO` on a read-only connection — not a file-level copy, since the real db runs in WAL mode and a copied `.db` file alone can miss committed rows still sitting in the uncheckpointed `-wal` sidecar. `--declare <file>` (TOML or JSON, by extension) lists `{ session_id, at, quest? | new? }` entries applied as `quest.declared`/`quest.created` events against the **copy** right after it opens — so history can be evaluated in declared mode without the source database ever holding hand-authored declarations; the copy's hero row is used, or a fresh one is seeded if the copy has none. Before rerunning, on the **copy only**, `resetRange` retracts (reason `eval reset`) every live trace whose `started_at` falls in `[from, to)`, then stints left with no live trace, then unconfirmed quests left with no live stint — the same cascade `dedupe.ts` uses, but selected by date range instead of duplicate grouping, since an earlier run's backfill for the same days already left its own traces/stints/quests in the source database, and without this reset the eval would mix that old cohort into the rerun's numbers and offer its stints to the classifier as reuse candidates. It also clears `w5_runs.session_note` and deletes `w5_windows` rows for the sessions touched, since the copy is throwaway and the rerun's `force` flag bypasses `w5_windows` coverage but would otherwise leave the copy inconsistent with what it records. It prints `eval: reset traces=<n> stints=<n> quests=<n>` before the rerun and `retracted_before_rerun traces=<n> stints=<n> quests=<n>` alongside the metrics. It then force-reclassifies every window in `[from, to)` against the copy via `backfill`'s `force`/`from`/`to` options (`force` bypasses `w5_windows`/legacy coverage entirely; `from`/`to` bound both the session query and each session's per-message window, so a session that runs past `to` is only classified up to `to`). All metrics — trace count, stint count, the ratio, median stint duration, `continues` link count, and the 20 randomly sampled stints — are computed over live rows with `started_at` (traces) / `opened_at` (stints) in `[from, to)` after the reset, so they describe the rerun only; `doubts` and unknown stint ids are summed straight from `apply.ts`'s real per-window run summary, and the validator's repair counters (`overlap_dropped`, `bounds_clamped`, `guess_defaulted`, `session_note_truncated`, next to `selector_defaulted`/`selector_ambiguous`) from `validateResult`'s result, not a placeholder. It also prints `doubts_answered` (belongs/declare questions resolved in range), `traces_unattributed` (traces whose stint has no quest), `declarations_skipped` (see below), `quest_proposed_on_matched`, `selector_defaulted` and `selector_ambiguous`, so a run shows how often the classifier omitted the quest on a stint that lacked one and how often it broke the exactly-one selector rule.

**Non-Claude attribution and origin_kind in reports.** `attributeNonClaudeEvidence` (`report/intent-queries.ts`) resolves each `gh_commits`/`monday_items` row in range to a quest at report time — never in the collectors, which stay pure mirrors — by joining the row's org/project to the `claude_sessions` row active at its timestamp (latest-started wins on overlap, a documented heuristic) and resolving that session's `currentDeclaredQuest`; a row with no overlapping session or no declaration at that instant is unattributed (`questId: null`), never invented. This is wired into both `daily.ts` (commit lines and Monday item lines gain an ` — <quest title>` suffix) and `project.ts` (the branch-row and Monday-row task-name cell gains the same suffix, with a branch's own commits searched in order for the first one that resolves), not just exercised by its own unit test. `queryStints`/`queryQuests` also carry `questOriginKind`/`originKind`, rendered by `daily.ts`/`project.ts` as an `(inferred)` suffix on the quest title whenever `originKind !== "declared"` — a declared quest gets no annotation, matching how `questConfirmed`/`[unconfirmed]` already works. `queryDoubtRows` returns one row per `belongs`-kind question in range with its org/project; `querySideQuestDoubts` sums it for a single org/project, and `weekly.ts` fetches `queryDoubtRows` once per day (like `stints`/`quests`/`sideQuests`) and filters it in-memory per project key, rather than re-querying per (day × project) pair.

**`w5 eval --declare` file handling.** `applyDeclareFile` (`w5/eval.ts`) wraps the file read and JSON/TOML parse in `InvalidDeclareFileError` — a missing file, malformed JSON/TOML, or a non-array top level all surface as `--declare file ...` messages with exit 1 (`runEvalCommand` in `w5/cli.ts` catches the error the same way `validateEvalRange`'s `InvalidEvalRangeError` already is), never a raw stack trace. Each entry may set `scope`/`parent_session_id`/`declared_by` (defaulting to `"session"`/absent/`"hero"`) alongside `session_id`/`at`/`quest`/`new`, passed straight through to `declareQuest` — so a file can declare a subagent's quest against its parent. An entry's `new` may carry a sibling `new_ref: "<key>"`, and a later entry may use `quest_ref: "<key>"` instead of `quest` to reuse the quest a prior entry just created; refs resolve in file order and an unknown `quest_ref` is an `InvalidDeclareFileError`. A `session_id` absent from the copy's `claude_sessions` still appends its `quest.declared` event (declarations are events, not FK-checked) but can never resolve to a trace/window, so it is logged and counted in `EvalMetrics.declarationsSkipped` (printed as `declarations_skipped=`) rather than silently accepted.

## Push sync (local schema)

Migration `0019_push_sync.sql` is the local half of `docs/specs/push-sync.md`; the network half is "Push sync (network)" below.

- **`events.uid`** is a global ULID and the replay order: `EventStore.read` (and so `rebuildAll` and `stateAsOf`) walks `ORDER BY uid` (then `id`, which only breaks ties between NULL-uid rows inserted by hand). `events.id` stays the local SQLite rowid and is meaningless across hosts. `EventStore.append` runs in one `IMMEDIATE` transaction that reads `MAX(uid)` and inserts `ulidAfter(newUlid(), max)` (`src/intent/ids.ts`): whenever the factory's value is not greater, the max plus a cryptographically random increment in 1..2^64 (carrying into the time part; overflowing 128 bits throws), so single-host uid order equals id order exactly, even across processes and after pulling a uid from the future. Never +1: every host that pulled the same future uid holds the same max, and a fixed successor made them all mint one uid, which the server's `ON CONFLICT DO NOTHING` then silently deduped (`test/intent/uid-successor.test.ts` pins this with two `bun -e` processes). Rows migrated from before 0019 are backfilled by `openDatabase` (`backfillEventUids`, `src/db/database.ts`) with **deterministic** uids (`legacyEventUid`), so every copy of one database backfills identical uids and two hosts that started from a copied `tempad.db` dedupe the shared history by uid: time = `recorded_at` ms clamped non-decreasing in id order; random high 40 bits = the row id, big-endian; random low 40 bits = the first 40 bits of SHA-256 over `recorded_at|kind|subject|payload`. A backwards or same-ms `recorded_at` therefore keeps id order. An id past 2^40 - 1 throws. The `ulidAfter` successor guard applies only when an existing uid is already above a row's deterministic one (a NULL-uid row inserted by hand after the migration) and gives up determinism for that row. It is a cheap no-op once no uid is NULL. `test/intent/replay-order.test.ts` pins this: a pre-0019 fixture with same-ms and backwards `recorded_at` rebuilds every projection table identically before (id order) and after the migration.
- **Tiebreaks that used `id` now use `uid`:** `w5/dedupe.ts` keeps the lowest uid; the latest-declaration queries (`intent/declarations.ts`, `w5/apply.ts`, `w5/window.ts`) order `at DESC, uid DESC, id DESC` (or the ASC fold). Any new query that orders events must use `uid`, never `id` or `recorded_at`.
- **`sync_host` / `sync_dirty` / `sync_local`.** `sync_local` is a one-row table (`id = 1`) holding this host's slug; `openDatabase(path, { hostSlug })` reads it first and writes only when the row is missing or holds a different slug (an upsert, even a no-op one, takes the write lock, so every read-only command used to fail behind a running sync), and every CLI call site passes `config.hostSlug`. `openDatabase` sets `PRAGMA busy_timeout = 5000` before anything else (`busyTimeoutMs` overrides it for tests); every CLI connection goes through it. `sync_host` is the host tag, written at insert time from `(SELECT host_slug FROM sync_local WHERE id = 1)` — NULL when there is no `sync_local` row (push fills it later). Push state is the separate `sync_dirty` column (`1` = not yet pushed, the default), never `sync_host IS NULL`. `events_no_update` now allows exactly three updates, with every other column unchanged (`IS`): fill a NULL `uid`, fill a NULL `sync_host`, change `sync_dirty` 1 to 0. Changing a set uid/host, re-dirtying (0 to 1), or touching content still aborts; `DELETE` is still forbidden.
- **Mirror sync columns.** `gh_repos`, `gh_commits`, `gh_pull_requests`, `monday_items`, `claude_sessions` and `claude_messages` gain `sync_host`, `sync_updated_at` (ms UTC ISO) and `sync_dirty`. Per table, triggers do the bookkeeping so collectors stay unchanged (only while sync is enabled; see "Trigger gate" below): `<t>_sync_insert` stamps, tags and dirties a row inserted with no `sync_updated_at` (a pull writes an explicit stamp and is left as written); `<t>_sync_update` does the same when the stamp is unchanged **and** a content column changed (`IS NOT`), so an identical re-upsert, marking a row pushed, or writing an explicit stamp never restamps; `<t>_sync_delete` upserts a `sync_tombstones(tbl, pk, deleted_at, sync_host, sync_dirty)` row whose `pk` is `json_array(<natural key>)` (e.g. `["acme/widgets",44]` for a pull request), refreshing it on a re-delete. Triggers match rows by `rowid`. **Stamps strictly increase per natural key on one host:** every new version is stamped `MAX(now, previous + 1 ms)` (previous = `OLD.sync_updated_at` for an update or a delete's tombstone, the key's tombstone `deleted_at` for an insert), so a burst within one millisecond never reuses a stamp, push's "mark pushed `WHERE sync_updated_at = <pushed>`" cannot clear a newer unpushed version, and last-writer-wins never ties two versions from one host. A re-insert leaves the old tombstone in place; it loses by stamp. **Host-local columns** (`localColumns` on each `SYNCED_UPSERT_TABLES` entry; today only `gh_repos.mirrored_at`) describe this machine, not the shared fact: they are not content, so the update trigger ignores them, push leaves them out and pull never overwrites them (a pulled new row has them NULL). `claude_sessions.claude_dir`/`file_path`/`file_mtime` stay content: only the owning host writes them and they are NOT NULL. **A column added to `events` must also be added to `events_no_update`'s column list, and one added to a mirror to its trigger in `src/sync/mirror-triggers.sql` (plus a migration: the transaction that applies every pending migration from 22 on runs `reconcileMirrorTriggers` once at its end) or to `localColumns`** — `test/migration-0019.test.ts` fails otherwise.
- **Trigger gate** (migration `0022_sync_trigger_gate.sql`, `src/sync/triggers.ts`). The 18 mirror triggers exist only when `sync_meta('mirror_sync_enabled')` is set; without it they are dropped, not `WHEN`-gated (even `WHEN 0` costs about half the full trigger on a 20000-row insert, because SQLite still builds the `OLD`/`NEW` row; numbers in `docs/specs/push-sync.md`, "Trigger gate"). `host_slug` is no gate: `sync claude` and `w5 run` write `sync_local` without `[sync]`. `src/sync/mirror-triggers.sql` is the one definition, byte-identical to what 0019 installed; `reconcileMirrorTriggers` makes `sqlite_master` match the marker (all 18 with that text, or none plus an empty `sync_tombstones`) and every pending migration from 22 on applies in ONE `IMMEDIATE` transaction (`applyMigrations` in `src/db/database.ts`, re-reading `user_version` under the lock so a second process that applied some of them is handled) that runs it once after the last step's SQL, then commits (one transaction, because 0022 drops the triggers and a commit between 22 and a later step would let another connection write mirror rows no trigger stamps or tombstones; reconcile only at the end, because the file describes the head schema, so installing it at an intermediate step would break a later step that touches a mirror whose column the triggers name before it exists); migrations below 22 keep one transaction each, so a chain that crosses 22 commits its pre-22 steps one by one and a failure from 22 on rolls back to the version the block started from, with that version's triggers (a database already at 22 stays at 22); `openDatabase` runs `ensureMirrorTriggers`, a read-only check that takes an `IMMEDIATE` transaction only to repair a difference. 0022 sets the marker when sync has evidently run (non-empty `sync_meta`, any `sync_cursors` row, or any event, tombstone or mirror row with `sync_dirty = 0`), keeping every pending row, event and tombstone; otherwise it deletes every tombstone. `runSyncEngine` calls `enableMirrorSync` first, which in one transaction sets the marker, restamps every mirror row as written now (`MAX(now, old stamp + 1 ms)`, `sync_host` = local host, dirty; every row, since a row 0019 stamped and changed while off would otherwise keep its old stamp and lose last-writer-wins to an older version another host pushed later) and installs the triggers; rows deleted while off get no tombstone. The marker is sticky: removing `[sync]` keeps the triggers and tombstones, since the remote still holds the rows; `tempad sync --forget` (below) is the one way out. Tombstones are pruned only while sync has never run: nothing records which hosts have pulled one (the server keeps no per-host cursor), so a sync-on prune cannot be proven safe. Tests that exercise the triggers open the database and then call `enableMirrorSync` (`openSynced` in `test/migration-0019.test.ts`; `openHost` in `test/sync/helpers.ts` does it for every sync test host, so a stamp a test stages before the host's first sync is not restamped by that sync's enable). `loadMigrations` lives in `src/db/migration-files.ts` so a test can spy it to stand in a longer chain.
- **A migration that rewrites mirror content must not restamp.** `<t>_sync_update` fires on any content change while the stamp is unchanged, so a plain `UPDATE` in a migration restamps the row with this host's slug and marks it dirty, which pushes a change every host would otherwise reach by itself. `0021_normalize_commit_dates.sql` shows the pattern: change `sync_updated_at` in the same statement as the content (the trigger's `WHEN` then fails), then put the original back in a second statement (also a stamp change, so also no trigger). `sync_host` and `sync_dirty` are never written, so a row pushed before stays clean and one not yet pushed stays dirty. Do not edit the triggers for this. 0021 rewrites every `gh_commits.authored_at`/`committed_at` ending in a numeric offset (`...-03:00`, what git's `%aI`/`%cI` gave before `toUtcIso`, b699db6) to `strftime('%Y-%m-%dT%H:%M:%fZ', ...)`, byte-identical to `toISOString()`; `Z` values and unreadable ones are untouched. A row pushed before 0021 stays offset-form on the server, so `LocalApplier.applyRow` (`sync/engine.ts`) rewrites `gh_commits.authored_at`/`committed_at` with `normalizeOffsetTimestamp` (`collect/github/log.ts`) before the upsert; the pull writes its own stamp, so no trigger fires and the row stays clean. That is what lets the reconcile query and the report queries compare `authored_at` as text (and use the `gh_commits_authored` index) instead of `julianday()`. `gh_pull_requests` timestamps come from the GitHub API (UTC `Z` in every fixture), not from `%aI`, so 0021 leaves them alone. **Offsets of +-15:00 or more** (git never emits them; imported history can) make SQLite's `strftime` return NULL, so 0021's COALESCE kept the offset text while `toUtcIso`/`applyRow` (JavaScript accepts up to +-23:59) write UTC. JavaScript is the canonical form. Migration `0023_normalize_wide_offset_commit_dates.sql` has no statements; its work is `normalizeWideOffsetCommitDates` (`src/db/database.ts`), registered for version 23 in `MIGRATION_STEPS`, which `applyMigrations` runs right after that migration's SQL inside the same IMMEDIATE transaction as the `user_version` bump. It rewrites whatever 0021 left with `normalizeOffsetTimestamp`, so it runs once per database, atomically with the version (a throw rolls back the rewrite and the bump; a backup restored from below 23 reruns it), costs nothing on later opens (no scan, no unlocked pre-read) and is serialized by the migration lock; an offset-shaped value that does not parse stays. A TypeScript half of a migration goes in `MIGRATION_STEPS`, keyed by version. It uses 0021's stamp trick (move `sync_updated_at` in the same statement, put it back in a second), never writes `sync_host` or `sync_dirty`, and so pushes nothing: every host computes the same text alone, and a pull of the same row compares equal under an equal stamp.
- **Table registry.** `src/sync/tables.ts` classifies every table as synced-append (`events`, key `uid`), synced-upsert (the six mirrors with their natural keys, in parent-first push order) or local-only (projections including `identity_aliases` and `membership_leaves`, `sync_state`, the w5 queue/runs/quiet tables, `sync_local`, `sync_cursors`, `sync_tombstones`, `sync_meta`). `test/sync/tables.test.ts` fails when any table in a migrated database plus every production projection's tables (`ALL_PROJECTIONS`, `src/intent/projections/register.ts`) is unclassified, so a new table must be placed deliberately.
- **Identity merge across hosts** (`src/intent/identity.ts`). Every host ran its own `hero init` / `party add` / `client add`, so a synced log has several `hero.created` and several `party.created`/`client.created` per slug. The first created event in uid order is canonical: one hero overall, one party per slug, one client per slug, one open membership per (hero, party). A later one inserts no row and records `alias_id -> canonical_id` in the `identity_aliases` projection (owned by the `heroes` projection, which is registered first so a rebuild clears it before anything writes; local-only). Reducers resolve hero/party/client/membership ids through `resolveIdentity`/`resolveOwnerIdentity` before writing: membership hero/party, `party.reworded`/`membership.left` subjects, saga/quest owners. **A membership alias is a join the hero still holds:** a `membership.left` ends only the original it names (recorded in `membership_leaves`, a local-only party-projection table), and the canonical row closes when every original (its own id plus its `membership` aliases) has left, with the last leave's time and reason; `tempad party leave` therefore appends one `membership.left` per open original (`openMembershipOriginals`, `src/intent/projections/party.ts`), and with a single original it is the old one-event close. **Opposite `quest merge`s from two hosts cannot loop:** the `quest.merged` reducer ignores a merge whose target already leads back to its source (`mergeWouldCycle`, `src/intent/projections/quest.ts`), so the earlier uid wins on every host; `resolveQuest` still follows chains. **A new reducer that reads one of these ids from a payload or subject must resolve it the same way.** Every "which hero" lookup goes through `currentHeroId` (never `SELECT id FROM heroes LIMIT 1`). Slugs compare exactly (`acme`, `Acme`, `acme-2` are three parties). Other projection keys cannot collide across hosts (audit in `docs/specs/push-sync.md`): sagas/quests/stints/traces/questions are keyed by per-event ULIDs, `impacts.subject` is an upsert where the later uid is the next revision, `w5_windows`/`trace_links` have no unique key, `projection_state` is per host. A single-host log records no alias, so offline projections are unchanged (`test/intent/identity-merge.test.ts`).
- **w5 stays host-local.** `backfill` takes `hostSlug?: string`; when set, only sessions with `claude_sessions.host_slug = hostSlug` are classified. `w5 backfill` and `w5 eval` (`EvalOptions.hostSlug`) pass `config.hostSlug` only when `isSyncEnabled(config.home)`, so a pulled session from another host is never classified twice; with sync off nothing changes. `isSyncEnabled` reads only `[sync]`, never the token, so w5 does not need `TEMPAD_SYNC_TOKEN`.
- **Test helper.** `openDatabase(path, { upToVersion: n })` stops migrating at version `n`, for building a database the way an older release left it (`legacy-chain`, `legacy-vocabulary`, `replay-order`, `migration-0019` tests). Never use it outside tests.

## Push sync (network)

`src/sync/`: `config.ts` (`loadSyncConfig`, `isSyncEnabled`), `engine.ts` (`runSyncEngine`, pure over a `SyncRemote` interface), `remote.ts` (`openRemote`), `run.ts` (`runPushSync`, `formatSyncSummary`). Spec: `docs/specs/push-sync.md`; server setup: `docs/deploy/sqld-coolify.md`.

- **Config.** `[sync]` in `tempad.toml` (`url`, `enabled` default `true`, `batch_size` default 500). No section or `enabled = false` returns `null` and nothing else is validated. `url` accepts `libsql:`, `https:`, `wss:`; `http:`/`ws:` only for loopback hosts. A query string or fragment (`@libsql/core` honours `?tls=0` and `?authToken=`), userinfo, and any backslash, whitespace or control character (WHATWG reads `\` as `/`, `@libsql/core`'s regex does not, so `http://127.0.0.1\@evil.com` would reach `evil.com` in plain text) are rejected, and the error never echoes the URL. `validateSyncUrl` returns a URL rebuilt from the checked parse, and `remote.ts` hands `createClient` only that, never the raw string. Every error is a `SyncConfigError` (invalid TOML included); `tempad sync` and the CLI's top-level catch print it as one `sync: <reason>` line, exit 1. `planW5Command` takes `syncEnabled` as a thunk and evaluates it only for `backfill`/`eval`, so a broken `[sync]` never breaks `w5 hook`, `enqueue`, `context`, `quiet` or `review`. `TEMPAD_SYNC_TOKEN` is in `ignoreWorkingDirectoryEnvFiles`'s guarded list. `TEMPAD_SYNC_TOKEN` is `loadConfig`'s `syncToken` (process env, else `TEMPAD_HOME/.env`; see "Per-command configuration"); `runSyncCommand` passes it to `runPushSync` as `syncToken` and `loadSyncConfig(home, token)` only checks it is non-blank (same `TEMPAD_SYNC_TOKEN is required when [sync] is enabled` text), so it is never read from the environment inside `src/sync/`.
- **Failures.** Anything after config validation that fails in `runPushSync` (`src/sync/run.ts`) -- the dynamic import of `remote.ts` (package missing), `openRemote`, network, auth, sqld down, schema gate, uid collision -- is rethrown as `SyncRunError`, whose message is the whole stderr line `sync: push failed: <reason>` (`pull` when only `--pull` was asked; the token scrubbed). `runSyncCommand` prints it, exits 1, and the collector summaries printed before it stay (and their rows are already committed). A bad `[sync]` stays a `SyncConfigError`, printed as `sync: <reason>`; `SyncNotConfiguredError` stays bare. `test/sync/failure.test.ts` drives the CLI against a loader that throws, a closed port, and loopback servers answering 401 and 500.
- **Offline guarantee.** `remote.ts` is the only file importing `@libsql/client`, and only the `/web` entry (no native binding). `run.ts` reaches it through `await import("./remote")` after `loadSyncConfig` returned non-null, so with sync off the module is never loaded. `test/sync/offline.test.ts` proves it by running the CLI under `bun --preload test/sync/libsql-guard.ts`, a Bun plugin whose `onLoad` replaces any `@libsql/client` module with one that throws (`onResolve` cannot be used: throwing there segfaults Bun 1.3).
- **Token hygiene.** The token is never logged, printed or put in an error. `run.ts` wraps every failure with `safeErrorMessage`, which also redacts the token if a library echoes it (only tokens of 16+ characters, so a toy token does not mangle messages).
- **Remote schema** (`REMOTE_SCHEMA`, created on first contact): `sync_meta` (`server_id`, `schema_version`), `sync_clock` (one row, `seq`), `sync_rows(tbl, pk, data, sync_host, sync_updated_at, seq)` for mirror rows and tombstones (`data` NULL), `sync_events(uid, data, sync_host, seq)`. Every write bumps `sync_clock.seq` and stamps the row with it; pull cursors (`sync_cursors`) are seqs.
- **Push.** The `sync_dirty = 1` rows are the outbox. Mirrors and tombstones page by rowid (the first page has no lower bound: an `INTEGER PRIMARY KEY` rowid is the source id, and 0 or negative ids are valid), events by uid, `batch_size` per page, each page one remote `write` (`client.batch(..., "write")`, a transaction). The remote upsert keeps the existing row unless `(excluded.sync_updated_at, excluded.sync_host) > (sync_updated_at, sync_host)`; events are insert-or-ignore by uid. A pushed row is marked clean with `WHERE rowid = ? AND sync_dirty = 1 AND sync_updated_at = <pushed stamp>`, so an edit made during the push stays dirty. A failed page leaves its rows dirty and the next run resumes there. Content columns exclude the sync columns and `localColumns`. Every push batch also raises the remote `schema_version` to the local `user_version`.
- **Pull.** Pages end on a seq boundary (`seq <= MAX(seq) of the first pageSize rows`), so a page never splits one seq. Each page is one local transaction with `PRAGMA defer_foreign_keys = ON`, and the cursor advances inside it. Local apply uses the same last-writer-wins rule (a NULL local `sync_host` counts as this host's slug). A winning remote row upserts with its remote stamp and host and `sync_dirty = 0`; a winning tombstone deletes the local row and rewrites the tombstone the delete trigger just wrote with the remote stamp and host, clean; a remote row that beats a local tombstone deletes the tombstone. When a tie on stamp is won by host, the local restamp trigger fires; a corrective update puts the remote stamp and host back. Pulled columns this schema does not have are dropped. Pull skips this host's own rows and events (`sync_host IS NOT ?`) except while `sync_meta('pull_own_pending')` is set: the unknown-server transaction sets it to a fresh ULID, and a pull that completes every page compare-and-deletes it. A host reinstalled under the same `HOST_SLUG` (empty db, unknown server) therefore gets its own history back. A `tempad.db` restored from an older backup looks known (same id, cursors, probes), so every run that is not already unknown also checks `ownHistoryMissing` before the push: the server's newest own event (uid not in local `events`) or newest own mirror row/tombstone (local row and tombstone both absent or older by `(stamp, host)`), read through the remote `(sync_host, seq)` indexes. A miss sets `pull_own_pending` and deletes the cursors in one transaction, never `reseed_pending`.
- **FK parents across pages** (addition to the spec). A pulled child whose parent row is neither local nor in the page (the parent was updated after the child, so its seq is later) would fail the deferred FK check. `LocalApplier.missingParents` finds them through `pragma_foreign_key_list`, `fetchParents` reads them from `sync_rows` by pk, and they are applied first, under the same rule, in the same transaction.
- **Schema gate.** Remote `schema_version` greater than local `user_version` throws `SchemaGateError` (`remote holds data from tempad schema N; upgrade tempad on this host (schema M)`) right after the idempotent remote bootstrap (create tables, seed `server_id` and `schema_version` if absent), before any row is pushed or pulled. When the remote version is lower, it is raised right after the gate (so a pull-only run still stops older hosts), and every push batch raises it again.
- **Server identity and re-seed.** Local `sync_meta.server_id` (migration `0020_sync_meta.sql`, local-only) is compared with the remote one. The server counts as unknown when the ids differ, when the remote clock is below this host's highest cursor, when a push probe is gone (`push_probe_event` = last pushed event uid, checked with `SELECT 1 FROM sync_events WHERE uid = ?`; `push_probe_row` = last pushed row/tombstone `(tbl, pk, stamp, host)`, checked with `(sync_updated_at, sync_host) >= (stamp, host)`), or while local `sync_meta('reseed_pending')` is set. Unknown writes `reseed_pending = <server id>` and deletes every `sync_cursors` row in one transaction, so every later run pulls from 0 and pushes everything until the marker clears; pull-only runs, a push that dies part-way and crashes leave it set. A re-seed push re-sends every row, event and tombstone this host holds, dirty or not and **whatever its `sync_host`** (each with its original host and stamp); only when it completes in full does one transaction store `server_id` and compare-and-delete the marker. When the clock or a probe shows lost writes under the stored id (a restore that kept its id), the host also rotates the remote `server_id` (compare-and-set on the old value, then re-reads it), so every other host sees a different id and re-seeds too, including hosts whose probes another host's re-seed already put back; a host that only sees a different id never rotates, so two detectors cannot ping-pong. Runbook: after restoring a backup, `DELETE FROM sync_meta WHERE key = 'server_id'` on the server, so every host mints a fresh identity. Pushing other hosts' rows lets one surviving host restore history written by retired ones; the server's conflict rule and `ON CONFLICT (uid) DO NOTHING` keep it idempotent.
- **Rebuild and the pending marker.** The transaction that inserts a pulled events page with any new event also sets local `sync_meta('rebuild_pending')` to a fresh ULID. `rebuildIfPending` reads the value and rebuilds (`registerAllProjections(); rebuildAll(database, { beforeCommit })`, overridable through `SyncRunOptions.rebuildProjections(database, options)`, which must call `options.beforeCommit`). `beforeCommit` runs `clearRebuildMarker(database, token)`, a compare-and-delete on the value read, inside `rebuildAll`'s IMMEDIATE transaction: a rebuild that rolls back keeps the marker, and a page pulled concurrently after the rebuild read its events has set a new value, so the marker survives for it. It runs at the start of every `runSyncEngine`, push-only included and before any network call, and again at the end; either one sets `rebuilt=yes`. A throw from the first one is caught: the run warns on stderr (`sync: projection rebuild failed, retrying after push and pull: ...`, through `SyncRunOptions.warn`), pushes and pulls anyway, and only the end-of-run retry failing fails the run. So a pull failing on a later page, a throw from `rebuildAll`, or a crash never leaves projections silently missing pulled events. Projections are never synced.
- **Pulled events** insert with `ON CONFLICT (uid) DO NOTHING`, never `OR IGNORE`: any other constraint violation throws and rolls the page back, so the cursor never skips an event. **Uid collisions are loud** (`EventCollisionError`): after each events batch commits remotely, the push selects those uids back and throws before marking them clean if the server holds different content; a pulled event whose uid exists locally with different content throws, rolling the page back and holding the cursor. Content is compared over the columns both sides carry.
- **Legacy events on copied databases.** Two hosts started from a copy of one pre-sync `tempad.db` share legacy uids but stamp them with their own `sync_host`. Harmless: events dedupe by uid.
- **Tests.** `test/sync/helpers.ts` has `FakeRemote` (the same SQL on an in-memory `bun:sqlite`, with `failOnWrite`) and snapshot helpers; `engine.test.ts` covers the conflict rule, ties, tombstones, two-host convergence (each host runs its own `hero init` and `party add`), no-op resync, partial push, schema gate, re-seed and the cross-page FK parent. `engine.test.ts` also covers a pull failing on a later page, a throwing rebuild, a constraint-violating pulled event, and a three-host history re-seeded by one host into a fresh fourth. Round 3 adds restores that kept their id (a pull-only run first, a re-seed interrupted part-way, another host writing first; a fourth host converges in each), the one-time `server_id` rotation, the start rebuild failing while push and pull still run, the marker compare-and-delete and its rollback inside `beforeCommit`, push- and pull-side uid collisions, and a rowid-0 mirror row. `sqld.integration.test.ts` runs the same scenarios plus the CLI against a real `ghcr.io/tursodatabase/libsql-server` container pinned by digest (`tempad-sqld-test-<hex>`, `--rm`, label `tempad-test=sqld`, one at a time). The name is recorded before `docker run`, so `afterAll` and a `process.on("exit")` hook remove it with `docker rm -f -v` even after a `beforeAll` timeout; each container also carries `tempad-test-owner=<hostname>:<pid>:<start ms>`; `beforeAll` sweeps only labelled containers whose owner ran on this machine and is gone, or that are older than 30 minutes (another machine's or an unowned one goes by age), and never one whose owner on this machine is alive, then pulls the image only when missing (300 s budget). When `DOCKER_HOST` or the docker context endpoint is `ssh://`, the published port lives on that remote host, so the test opens an `ssh -N -L` tunnel to it. Skipped, with the reason printed, when the `docker` CLI is absent or `docker info` cannot reach a daemon.

## Schedule

`tempad schedule install | remove | status [--json]` (`packages/core/src/schedule/`) keeps an hourly per-user `tempad sync` running. `definitions.ts` is pure text (`renderLaunchdPlist`, `renderSystemdService`, `renderSystemdTimer`, and the parsers `status` reads them back with), `index.ts` writes files and drives `launchctl`/`systemctl` through an injected `CommandRunner`, so tests never reach the real service manager and never install anything on the machine. Paths come from `process.env.HOME` (and `XDG_CONFIG_HOME`, absolute only; it is in `USER_SCOPED_VARIABLES`), never `os.homedir()`; every function takes the environment as a parameter, so tests pass an object instead of mutating `process.env`.

- **macOS:** `~/Library/LaunchAgents/sh.hyperlab.tempad.sync.plist` (`StartInterval` 3600, `RunAtLoad`); install is write, `bootout` (ignored), `enable`, `bootstrap gui/<uid>` (retried 5 x 500 ms: `bootout` returns before launchd has finished with the old job); remove is `bootout` plus delete; `status` parses `launchctl print` (`state`, `runs`, `last exit code`) and uses `sync.log`'s mtime as the last run, because launchd records no time. **Linux:** `$XDG_CONFIG_HOME|~/.config/systemd/user/tempad-sync.{service,timer}` (`OnCalendar=hourly` with `Persistent=true` so a missed hour catches up; no `OnActiveSec` and no `OnUnitActiveSec`, either would add a second trigger next to `OnCalendar`/`Persistent` and run two full syncs); install is `daemon-reload`, `enable --now`, `restart` on a reinstall, then `start --no-block` of the service for the first run now (launchd's `RunAtLoad`; `--no-block` because a oneshot `start` waits for the whole sync). A reinstall after a missed hour can run twice back to back (Persistent catch-up plus the explicit start): the lock skips the second if the first is still running, and otherwise it is a quick no-op sync; `status` parses `systemctl --user show`. Other platforms: error, exit 1.
- **The job runs what the user invoked:** `[runtime, "--no-env-file", realpath(argv[1]), "sync"]` (`resolveInvokedEntry`; `--no-env-file` because the shebang flag does not apply to `bun <file>`). `resolveRuntime` skips `PATH` entries under `~/.proto/tools/` and `dirname(execPath)` (the proto shim prepends its versioned directory to `PATH` before it execs bun, so inside bun it precedes `~/.proto/shims`), then takes the first `bun` on the caller's absolute `PATH` when it sits in `~/.proto/shims`, `~/.bun/bin`, `/opt/homebrew/bin` or `/usr/local/bin` (a `process.execPath` of `~/.proto/tools/bun/<version>/bun` would pin the job to a Bun that the next upgrade deletes); when `execPath` is under `~/.proto/tools` and nothing stable is on `PATH` it checks `$PROTO_HOME/shims/bun` (default `~/.proto/shims/bun`; `PROTO_HOME` is in `USER_SCOPED_VARIABLES`) directly. Through a shim the version would be proto's resolution in the job's working directory (`TEMPAD_HOME`), which is proto's global default and not the installing checkout's `.prototools` pin, so `resolveInvokedEntry` returns `bunPin` (`readBunPin`: the nearest `.prototools` above the realpath of the entry script with a string `bun`, nearer files winning and a file without one letting the search continue, the value passed through as written, and the search ending at the project root: a directory with `.git` (a file in a worktree) or the root of a package under `node_modules`, so `~/.prototools` or a stray ancestor is never taken for the project's pin; the root's own `.prototools` is read before the stop applies) when, and only when, the runtime is `$PROTO_HOME/shims/bun`, and the job carries it as `PROTO_BUN_VERSION` (an `Environment=` line / plist `EnvironmentVariables` entry, `ScheduleJob.protoBunVersion`). Chosen over a working directory in the checkout (a global install has none, and the job would depend on its location) and over the versioned binary `~/.proto/tools/bun/<v>/bun` (bypasses proto and breaks when proto prunes it): the shim stays the stable path, the env var is proto's own highest-precedence override and is independent of the working directory. No pin above the script means no variable, so proto's default decides. An exact pin that proto has not installed is an `install` warning (`proto install bun <v>`). Otherwise `process.execPath`, with an `install` warning when its path has a version segment and a refusal when it is disposable. `PATH` = the runtime's directory, then the caller's absolute `PATH` entries, then the usual tool directories. `TEMPAD_HOME` is carried only when it was set, `~` expanded against `HOME` and a relative value made absolute (`resolve`). `install` warns (stderr, never the value) when a variable a collector needs (`needs` of each collector, plus `GH_TOKEN`, `TEMPAD_SYNC_TOKEN`, `HOST_SLUG`) is set in the shell but absent from `TEMPAD_HOME/.env`: the job inherits no shell exports. An entry under the temp directory or the bunx cache (`isUnstableInstallPath`) is refused. `install` also refuses a home that is not set up, and writes `TEMPAD_HOME/logs/sync.log` as stdout and stderr. `status` exits 0 only when installed, loaded and no problem (missing runtime or entry, a non-zero last exit code, a Bun that does not start) was found. It also runs `<runtime> --version` (`CommandRunner` takes `{ env, cwd }`) with the environment read back from the definition (`parseLaunchdEnvironment`/`parseSystemdEnvironment`) plus `HOME`, in `TEMPAD_HOME`, and `PROTO_AUTO_INSTALL=false` so a check never downloads a Bun, and prints `bun: <version>` (`bunVersion`, `bunPinned`, `bunViaProtoShim` in `--json`), so the line is what the job resolves through the shim, not a guess from the pin. For a shim job it also reads the checkout's current pin (`bunCheckoutPin`) and reports a problem (exit 1) when it differs from the baked one or the job has none: the baked pin goes stale when the checkout moves to another Bun, and the fix it names is `tempad schedule install`.
- **`tempad sync` takes `TEMPAD_HOME/sync.lock`** (`src/sync/lock.ts`, `using` so every return and throw releases it) after the `--forget`/`--rejoin` branches, so a scheduled run that overlaps a manual one skips with a stderr message: exit 0 for a plain sync, 75 (EX_TEMPFAIL) for `--push`/`--pull`. It is the `w5.lock` mechanism, one implementation (`tryClearStaleLock`, `src/w5/lock.ts`, shared by `w5 enqueue`/`w5 run` through the boolean wrapper `clearStaleLock`), with one difference: a lock whose pid is gone and is not this process is cleared at once (`deadRunnerGraceMinutes: 0`; `checkLock` never judges this process's own pid dead), because a sync killed by SIGINT/SIGTERM leaves one behind and the 30 minute grace would make every run in that half hour say "already running". Every clear, dead-pid or age-based (30 minutes, no pid, 6 h ceiling), is serialized by `<lock>.clearing` (`clearingPathFor`, `O_EXCL`, held only while the lock is judged a second time and unlinked): the unlink happens only inside it, after that second judgment, and nothing can replace an existing lock file (`O_EXCL` fails; `releaseLock` removes only its own pid's), so one run cannot remove another's fresh lock. Check-then-unlink without it let two runs both judge one lock stale and both take it (`test/w5/lock.test.ts` races 8 real processes over each rule for both locks and asserts one winner; the `afterJudgedStale`/`beforeUnlink` seams widen the windows, and without the handoff all five cases fail). The one gap left is `releaseLock` unlinking by path after reading the pid, which can take down a lock a third run just acquired only when its holder was cleared as past the 6 h ceiling at that very moment. A run that finds the clearing lock taken skips; an abandoned one is removed by the next run (`removeAbandonedHandoff`: rename aside, delete only if it is the identity that was judged abandoned (inode, mtime, pid text), else `link` it back, so a second run judging the same abandoned handoff cannot delete the fresh one the first took), which then retries its own clear once (so it does not report a sync that is not there): its pid is gone, or it names no pid and is older than `CLEARING_STALE_MS` (10 s; the critical section is microseconds), or it names a live pid and is older than `STALE_LOCK_MINUTES` (a clearer stopped by SIGSTOP or a sleeping laptop between its second judgment and its unlink is still the clearer, and deleting its handoff at 10 s would let it unlink a newer lock when resumed; only a reused pid outlives the 30 minutes), so a dead `sync.lock` can never wedge every sync (the one remaining race needs a crash inside the critical section plus two simultaneous cleanups). The held `sync.lock` is touched every `SYNC_LOCK_TOUCH_MS` (5 min, an unref'd interval that touches only a lock still holding this pid) as `w5 run` touches before each job, so a sync longer than the 6 h ceiling is not taken over. A lock with no pid yet is left to the age rule; a reused live pid can keep a dead run's lock up to the 6 h ceiling. It exists because the collectors share one git mirror directory (`git clone --mirror`/fetch would collide on git's own locks) and would fetch the same pages twice; the database itself tolerates overlap (every write waits up to `busy_timeout`, every upsert is idempotent), and a `w5 run` re-syncing one session file is likewise safe next to `sync`. An unconfigured home gets no lock file.
- **`tempad scry`** adds a `schedule` check and recommendation (`probeSchedule`, a filesystem-only read) only when a collector is stale: no schedule installed recommends `tempad schedule install`; one installed but still stale recommends `tempad schedule status`. Fresh collectors add nothing.

## Projects

`[[projects]]` rules in `tempad.toml` are either `pattern` (a `URLPattern` with named groups, e.g. `~/work/:org/:project/:rest*`) or `path` (one exact folder, `~` expanded, matching that folder and everything under it) — a rule has exactly one of the two. `path` rules need static `org`/`project` (there is nothing to extract a group from); `pattern` rules can supply `org`/`project` statically or via a named group. Either kind can add `name` for a human display label; `resolvePath` returns it as `ResolvedPath.name`, filled into `claude_sessions.project_name` by the Claude collector. Reports show `<name>` in place of `org/project` wherever every session in the group shares one (`projectLabel` in `src/report/format.ts`). List path rules before pattern rules — first match wins, and a path rule is normally more specific. `tempad project register` prepends new `path` rules for exactly this reason.

`path` matching (`normalizePathForMatch`/`matchesPath` in `src/config/rules.ts`) normalizes both the rule's folder (at load time) and the `cwd`/query path (at match time) the same way: `~`-expand, resolve symlinks with `realpathSync` when the path exists on disk (fall back to plain `path.resolve` when it doesn't — a not-yet-created subfolder under a symlinked path won't resolve the symlink component until it exists), strip a trailing slash, then compare case-insensitively on darwin only (`process.platform`), exact elsewhere. `reresolveSessions` (`src/collect/claude.ts`) and `tempad project register|reresolve` (`src/cli.ts`, which always expands `~` with `os.homedir()`, never `process.env.HOME`) use the same normalization, so a hand-typed path with a trailing slash, different case, or reached through a symlink still matches the sessions it should.

## Release

- Two artifacts ship from this repo: the npm package `tempad` (`packages/core`) and the Claude Code plugin `tempad` (`.claude-plugin/plugin.json` at the root; the marketplace `hyperlab-sh/claude-plugins` lives elsewhere and this repo never carries a `marketplace.json`).
- The version lives in `packages/core/package.json` and `.claude-plugin/plugin.json` and the two must match; `packages/core/test/release.test.ts` fails otherwise. Bump both together, move the `CHANGELOG.md` `[Unreleased]` entries under the new version, and commit.
- The npm tarball is whitelisted by `files` in `packages/core/package.json`: `src` (migrations are read from `src/db/migrations` through `import.meta.dir`), `skills`, `hooks`, `README.md`, `LICENSE`. `tempad.example.toml` and `.env.example` are deliberately not shipped. Anything the runtime resolves with `import.meta.dir` must stay inside `packages/core`, or an installed copy breaks. `packages/core/LICENSE` is a copy of the root one (the test checks they match).
- Check a release locally: `cd packages/core && bun pm pack`, install the tarball into an empty directory with fresh `HOME` and `TEMPAD_HOME`, and run `bunx @hyperlab.sh/tempad --help`. `bun publish --dry-run` lists the files (it then stops at "missing authentication" unless logged in).
- Publishing is `bun publish` from `packages/core`, run by the operator. Agents never publish.
- Outside the repo, the proto `bun` shim may pick a newer Bun than `.prototools` pins; for a faithful check call the pinned binary (`~/.proto/tools/bun/1.4.2/bun`) and print `--version`, since the shim can answer with another one.

## Gotchas

- `runMigration` (`src/db/database.ts`) splits a migration on `;` before it drops `--` comment lines, so a semicolon inside a comment of an `ALTER`-only migration breaks its tolerant path (the file then runs as one script and fails with `no such table` on a database whose projection tables were never created). Keep semicolons out of migration comments.
- Monday.com's API `people` column filter by numeric id returns nothing. Filter client-side by name or id from the column's JSON value.
- Running `bun src/cli.ts` from a project directory auto-loads that project's `.env` into `process.env` (the shebang flag does not apply to `bun <file>`); the CLI strips tempad's variables back out, but tests that spawn it must still pass an explicit `env` and a fresh cwd.
- Claude session `.jsonl` files mix timestamped message lines with untimestamped metadata lines (`custom-title`, `agent-name`, `bridge-session`). Join them on `sessionId`.
- Bun's TOML parser is lax about some malformed input, and older versions were laxer: 1.3.14 accepted `[w5` at end of file, `[sync]]`, `[[a]`, a duplicate `[a]` table, `a = @` (the string `"@"`) and `url = libsql://x` (`"libsql:"`), which 1.4 rejects. `.prototools`, CI (`.github/workflows/ci.yml`), `.moon/toolchain.yml`, `packageManager` and `engines` all say 1.4.2, so a test that expects a TOML syntax error can use any malformed input 1.4.2 rejects (the scry test uses `model = = 1`). Typed reads (`[sync].enabled`, the url check) still catch what the parser lets through. Raising the pin means changing all of those together; `test/release.test.ts` pins `engines`.
- Git history rewrites: collectors re-scan an overlap window and delete rows whose sha is no longer reachable from any ref in the mirror.
